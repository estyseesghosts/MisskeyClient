# Exploration task: finish the notification codec boundary

## Scope

Investigate the current Beeline notification persistence code and produce a safe refactor plan that moves notification JSON encoding and decoding out of `NotificationRepository.kt` and into `NotificationJsonCodec.kt`.

This is an exploration task. Do not change application code. Do not create additional subagents.

The current checkout is authoritative. In v0.2.1, a large block of codec logic was still inside `NotificationRepository.kt`, roughly in the historical lines 520 through 1,115. Use that only as a location clue. Find the equivalent code in the current checkout before you make a recommendation.

## Goal

`NotificationRepository.kt` must own repository behavior.

`NotificationJsonCodec.kt` must own the JSON serialization contract for repository notification state.

Codec helpers must not remain in the repository only because they were written there first.

This refactor must not change notification behavior or stored-data compatibility.

## Investigation

Read the current versions of:

- `NotificationRepository.kt`;
- `NotificationJsonCodec.kt`;
- notification repository state models;
- notification domain models;
- notification storage code;
- notification migration or legacy-import code;
- notification tests and protocol fixtures;
- current bug and work logs that mention notifications.

Map every encode and decode helper that participates in persisted notification JSON.

For each helper, identify:

- its inputs and outputs;
- which fields it writes or reads;
- optional and default values;
- enum handling;
- unknown-value handling;
- nested object handling;
- list and map handling;
- time and identifier handling;
- any dependency on repository state or behavior.

Separate pure serialization logic from repository behavior. If a helper performs both, describe how to split it without changing the data contract.

## Compatibility requirements

Treat persisted notification data as a compatibility boundary.

Do not use this refactor to redesign the JSON format.

Do not rename keys, change defaults, normalize values, remove tolerated legacy fields, or change unknown-value behavior unless a separate bug fix is explicitly approved.

Preserve behavior for missing, null, malformed, old, and unknown values where the current code intentionally supports them.

Check whether old app versions can have written data that the current version still reads.

Check whether moving private or top-level helpers changes visibility in a way that creates new coupling.

The v0.2.1 bug log reported notification JSON concerns, including loss of an unknown activity destination. Determine whether that issue still exists. Do not silently combine an unrelated behavior fix with the extraction. Record it separately if it remains.

## Verification strategy

Before implementation, identify tests that characterize the current format.

The plan must include regression coverage for:

- encode and decode round trips;
- representative notification types;
- notification actions and destinations;
- optional fields;
- unknown or unsupported values where supported;
- old persisted JSON;
- malformed data behavior;
- repository state serialization;
- any legacy import path that uses the same contract.

Prefer fixed compatibility fixtures for old stored JSON. A round-trip test alone is not enough because an encoder and decoder can change in the same wrong way.

Identify the focused notification test suites that must pass after the move. Also identify any broader tests needed for notification sync, launch routing, persistence, or account isolation.

## Refactor constraints

Move ownership, not behavior.

Keep the repository API stable unless there is a strong reason to change it.

Do not make protocol mappers depend on persistence JSON.

Do not make `NotificationJsonCodec.kt` responsible for network payload parsing.

Do not combine this work with notification UI changes, sync redesign, database migration, or push-registration changes.

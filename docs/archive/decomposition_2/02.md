# Exploration task: separate the default Unicode emoji data

## Scope

Investigate the current `EmojiPicker.kt` and produce a small refactor plan to move the built-in Unicode emoji data into `DefaultUnicodeEmoji.kt`.

This is an exploration task. Do not change application code. Do not create additional subagents.

The current checkout is authoritative. The v0.2.1 code is historical context only.

## Goal

`EmojiPicker.kt` should own picker behavior and presentation.

The large built-in Unicode emoji data set should live in `DefaultUnicodeEmoji.kt`.

This task is an ownership cleanup. It must not change the emoji set or picker behavior.

## Investigation

Find the current built-in Unicode emoji declaration and every reference to it.

Check:

- its current symbol name;
- package and visibility;
- whether tests access it directly;
- whether ordering is user-visible;
- whether duplicates are meaningful;
- whether grouping or search code depends on its exact contents;
- whether initialization cost or mutability matters.

Determine the least disruptive location and API for the moved data.

Use the requested filename `DefaultUnicodeEmoji.kt` unless the current repository has a strong structural reason that makes this impossible. If such a reason exists, explain it.

## Requirements

Move the data without editing the data.

Do not reorder, deduplicate, expand, normalize, or update the Unicode emoji list as part of this refactor.

Do not combine the move with picker search changes, grouping changes, favourites changes, server emoji changes, or UI changes.

Keep visibility as narrow as practical.

Do not expose a mutable collection when the current callers do not need one.

Do not create a new object hierarchy only to hold one static data set.

## Verification

The plan must preserve:

- picker ordering;
- search results;
- grouping behavior;
- selection behavior;
- tests that depend on the default list.

Identify any test that should be moved or added to make accidental list changes visible.

## Required output

Return one Markdown report in the project writing style.

Use these sections:

1. `Current data ownership`
2. `Current consumers`
3. `Proposed extraction`
4. `Behavior that must stay unchanged`
5. `Refactor order`
6. `Verification`
7. `Risks and open questions`

Keep the plan short unless the current checkout contains unexpected coupling.

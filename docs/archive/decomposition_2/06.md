# Exploration task: audit Beeline for remaining structural defects and hidden bugs

## Scope

Perform a broad read-only audit of the current Beeline codebase after the recent refactor work.

This is an exploration task. Do not change application code. Do not create additional subagents.

The current checkout is authoritative. Use v0.2.1 only to understand historical pressure points. Do not report a v0.2.1 problem as current until you verify it in the current checkout.

The goal is to find remaining spaghetti code, wrong ownership, logic defects, race conditions, state bugs, unsafe compatibility assumptions, and test blind spots that automated and manual testing may not have caught.

## Start with existing project evidence

Read the current:

- project writing guide;
- `README.md`;
- `logs/BUGS.txt`;
- `logs/DONE.txt`;
- `logs/TODO.txt`;
- relevant tests;
- recent refactor commits or change history available in the checkout.

Known findings are not new findings. Check whether they are fixed, still present, or changed.

The v0.2.1 bug log already identified concerns around preference writes and failures, moderation paging, notification JSON, checkpoint account validation, optimistic rollback, reaction overlays, Misskey parent loading, Mastodon reaction capability handling, Home paging, product identity, storage, Room schema debt, thread limits, rendering work, lifecycle and origin handling, and localization.

Use those items as a regression checklist. Then search beyond them.

## Audit method

Do not rank files only by line count.

Large static data files are not automatically design problems. Focus on files that combine several responsibilities, own mutable state, coordinate asynchronous work, translate protocol data, persist state, or sit on many dependency paths.

For each suspicious area, trace behavior across its callers and tests before you report a defect.

Pay special attention to:

- long-lived coroutine scopes and cancellation;
- work launched without a clear owner;
- stale state captured by callbacks;
- multi-account state leakage;
- account switching during in-flight work;
- optimistic UI updates and rollback;
- paging cursors and filtered counts;
- error swallowing and fallback behavior;
- temporary network failures being treated as permanent capability failures;
- serialization compatibility;
- Room migrations and retained data;
- duplicate sources of truth;
- feature logic placed in presentation files;
- presentation logic placed in repositories;
- protocol-specific behavior leaking into shared domain code;
- Mastodon-compatible server differences;
- Misskey-compatible server differences;
- navigation state restoration;
- lifecycle-sensitive Android behavior;
- API-level guards;
- Compose state stability and recomposition;
- unnecessary blocking work on the main thread;
- expensive work inside composition or frequently repeated paths;
- missing bounds on caches, lists, threads, or retained records;
- silent data loss;
- unsafe assumptions that tests only cover with ideal fixtures.

Use the historically large and stateful areas as starting points, not as a fixed target list. Check the current equivalents of app-shell code, notification code, protocol sources, UnifiedPush registration, account management, profile and thread state, media UI, preferences, and other files that now carry broad responsibility.

## Bug standard

Do not report style preferences as bugs.

Every bug or high-risk defect must include:

- current file and symbol;
- observed code path;
- why the behavior is wrong or unsafe;
- user or maintenance impact;
- confidence level;
- existing test coverage;
- the missing test or reproduction that would prove the issue.

If you cannot prove a defect, label it as a risk or investigation item.

Do not invent runtime evidence.

## Structural standard

Report a structural problem when it has a concrete maintenance cost, such as:

- one feature change requires edits through unrelated layers;
- one file owns unrelated responsibilities;
- a lower layer imports a feature-specific higher layer;
- state ownership is unclear;
- the same rule exists in several places;
- a generic object is becoming a dumping ground;
- tests require broad app construction for narrow behavior.

Recommend boundaries, not cosmetic file splitting.

A smaller file is not automatically a better design.

## Required output

Return one Markdown report in the project writing style.

Use these sections:

1. `Executive summary`
2. `Known findings rechecked`
3. `New correctness findings`
4. `New structural findings`
5. `Concurrency and lifecycle findings`
6. `Persistence and compatibility findings`
7. `Protocol boundary findings`
8. `UI state and Compose findings`
9. `Test blind spots`
10. `Recommended refactor order`
11. `Verification plan`
12. `Items that need runtime or live-server evidence`

For findings, use severity levels `critical`, `high`, `medium`, and `low`.

Separate confirmed defects from plausible risks.

Prefer a small number of well-supported findings over a long list of weak guesses.

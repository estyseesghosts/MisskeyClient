# Finish the Beeline refactor

You are to use the six completed exploration reports provided with this task to finish the Beeline refactor.

This is an implementation task.

Do not produce another broad refactor plan and stop there.

Read the reports. Verify their findings against the current checkout. Then fix the code.

The current checkout is authoritative. File names, line numbers, signatures, and implementation details in the exploration reports are evidence from the checkout that the explorers reviewed. They are not permission to ignore newer changes.

If the source has changed since an exploration ran, trace the current implementation and apply the intent of the finding to the current code.

Follow `AGENTS.md` and `importantdocs/writing_style.md`.

Use Beeline as the product name.

`Palustris` is an internal historical identifier. Do not introduce it into user-facing text or new product documentation.

Do not use subagents unless you are explicitly told to use them.

## Goal

Finish this refactor in a way that leaves Beeline substantially easier to maintain.

Do not merely make the named files shorter.

Fix ownership.

Reduce coupling.

Remove accidental dependencies.

Fix the confirmed correctness defects found during the audit.

Add the tests required to keep those defects from returning.

Begin the permanent documentation structure described by the documentation exploration.

When this work is complete, adding an ordinary feature must not require threading unrelated parameters through the entire application shell.

A repository must not own presentation behavior.

A presentation file must not own generic application services.

Persistence codecs must not live inside repositories because they happened to be written there.

Large files must not become collections of unrelated responsibilities.

Tests must not need to construct most of the application to verify one screen.

Documentation must not become stale optional material.

## 1. Repair confirmed correctness defects first

The structural audit found real correctness problems.

Recheck each finding against the current source.

If it is still present, fix it before or alongside the structural work that owns it.

At minimum, recheck and resolve:

- stale Feed paging responses that can publish after refresh;
- stale direct-message requests that can publish into the wrong selected conversation;
- notification checkpoint queries that are not validated against their caller;
- moderation removal state that can remain stuck after a concurrent refresh;
- thread reaction overlay state that can apply the wrong `myReaction`;
- Saved Posts mutation families that can restore stale whole-post state;
- Mastodon reaction capability probing that treats an inaccessible arbitrary status as proof that the capability is unsupported;
- missing foreign-origin validation at the Misskey post boundary;
- Home automatic paging that compares filtered visible rows against an unfiltered backing collection;
- cancellation handling in long-lived cleanup or registration work where broad exception handling can swallow coroutine cancellation;
- notification Room corruption behavior;
- settings subpage restoration where plain `remember` loses state across recreation.

Do not change an item only because an exploration mentioned it.

Confirm the current path first.

### Stale asynchronous responses

For Feed and direct messages, add deterministic tests before the fix.

Use delayed or non-cooperative fakes.

Prove that an old request cannot publish after:

- refresh;
- account or session replacement;
- target or conversation replacement;
- another newer request taking ownership.

Use request generation, target identity, cursor identity, or another explicit publication guard appropriate to the existing owner.

Cancellation alone is not sufficient.

### Protocol capability detection

Do not convert a resource-specific `403`, `404`, `429`, or transient server failure into a permanent server capability decision.

Preserve the distinction between:

- supported;
- unsupported;
- unknown;
- temporarily unavailable;
- denied for this resource or account.

Do not make capability detection depend on one arbitrary status existing.

### Origin validation

Authenticated protocol adapters must reject foreign entity origins at their public boundary before network access when the operation requires an entity from that connection.

Do not rely on every caller to perform this validation correctly.

## 2. Fix the application dependency surface

The app-shell exploration found the central architecture problem.

`PalustrisApp` must stop being a giant flat integration boundary.

Do not replace approximately one hundred parameters with one approximately one-hundred-field `AppDependencies` class.

That is the same architecture with different punctuation.

### Preserve the correct existing owners

Do not move application-lifetime responsibilities into Compose to make signatures smaller.

Keep the existing authorities for:

- accounts and sessions;
- source construction;
- notification synchronization;
- foreground notification streaming;
- persistence;
- protocol adapters.

Keep `MainActivity` focused on Android entry-point responsibilities.

Keep `ConnectedApp` as a composition boundary, but stop using it as a giant value-forwarding function.

Keep `PalustrisApp` focused on application presentation, navigation, overlays, and other real shell state.

### Introduce focused feature contracts

Group state and actions only when they have one logical owner and one presentation responsibility.

Use the exploration findings as the starting map.

The final structure should have focused contracts for areas such as:

- account switching;
- connected account/session context;
- Home feed;
- Search;
- Photo Grid;
- Profile;
- Thread;
- Bookmarks;
- Likes;
- Notifications;
- Direct messages;
- Emoji picker/catalog;
- Composer and drafts;
- post action presentation;
- per-account notification settings.

These names are descriptive. They are not mandatory final type names.

Do not create one global feature contract containing all of them.

Do not expose repositories, ViewModels, access tokens, `SocialSource`, or storage implementations through the final presentation boundary.

Keep account ID, runtime session generation, and durable session revision semantics distinct where the current behavior requires them.

### Remove pass-through dependencies

Find values that cross a layer without being used there.

Eliminate unnecessary forwarding instead of grouping it.

In particular, recheck the findings about:

- `actionSource`;
- `DraftStore`;
- duplicate `ownedPosts`;
- content-warning policy already available through composition locals;
- active-account notification settings versus settings-route notification settings;
- dead callbacks;
- other parameters that now exist only because the old shell required them.

There must be one clear source of truth for a piece of state.

### Cross-surface post updates

The current update fan-out between Feed, Saved Posts, Likes, Profile, Notifications, and Thread is a real responsibility.

Give it one narrow owner.

That owner may coordinate normalized post projections between account-scoped state owners.

It must not become a new god object.

Keep its scope limited to:

- normalized post updates;
- registered sinks;
- account checks;
- session-revision checks;
- publication fan-out.

Do not move navigation, UI state, settings, protocol requests, or unrelated application services into it.

### Compose behavior

Be careful when converting flat arguments into contracts.

Do not introduce:

- unstable contract objects recreated unnecessarily on every recomposition;
- stale callback capture;
- retained objects from an old account;
- scopes that outlive their intended owner;
- source instances that differ between models which must share one source;
- loss of saveable navigation state.

Key account-scoped owners with the current account and session identity required by their behavior.

## 3. Fix tests that currently know too much

The app-shell tests must become easier to construct.

Do not create a production `AppDependencies` bag for tests.

Create focused test fixtures or helpers.

A test for Home should not need to understand Profile, notifications, direct messages, settings, and every other shell action.

Provide safe empty feature contracts where a test only needs shell presentation.

Prefer focused helpers such as:

- show a feed;
- show a profile;
- show notifications;
- show a thread;
- show a direct-message state.

Keep test action recorders in test code.

Use explicit in-memory storage for deterministic storage-sensitive tests.

Do not let a production Compose fallback silently select SharedPreferences only to make tests easier.

Keep leaf-screen tests as leaf-screen tests.

Use a real `MainActivity` only when the test genuinely needs activity recreation, Android window behavior, Hilt startup, API-level behavior, or other real activity integration.

## 5. Finish the notification codec boundary

Move persistence JSON codec ownership out of `NotificationRepository.kt`.

`NotificationRepository` owns repository state and synchronization behavior.

`NotificationJsonCodec` owns notification persistence JSON.

Do not redesign the stored format during this move.

### Add compatibility tests first

Before moving codec code, add fixed version-2 JSON fixtures.

Round-trip tests are not enough.

An encoder and decoder can make the same mistake and still pass a round trip.

Cover historical and edge cases identified by the exploration, including:

- old stored objects with omitted newer fields;
- legacy reaction `imageUrl`;
- target-only navigation;
- old connected push registration fields;
- unknown enum values;
- malformed array entries;
- every unread state;
- settings, including empty category sets;
- checkpoints with opaque cursors;
- dismissal IDs;
- delivery claims and leases;
- push registration failures;
- grouped notifications;
- recursive quotes;
- nullable interaction counts;
- custom emoji.

Treat notification JSON version `2` as an installed compatibility contract.

Do not:

- rename keys;
- change discriminants;
- change defaults;
- change omission behavior;
- change exception boundaries;
- reinterpret opaque cursors;
- normalize identifiers;
- create a new common enum policy;
- silently add fields that the current codec omits.

### Move codec logic, not repository behavior

Move recursive notification serialization helpers to `NotificationJsonCodec.kt`.

Make helper visibility narrow.

The stores should use the state-level codec boundary.

Do not move into the codec:

- repository synchronization;
- generation checks;
- page merging;
- query matching;
- read-state behavior;
- delivery claiming;
- storage deletion;
- protocol mapping;
- network payload parsing.

Move storage-identity or Android-delivery-identity helpers to their correct owners only in separate behavior-neutral slices if they still need cleanup.

### Separate discovered behavior defects

The codec exploration identified existing persistence omissions and corruption-policy questions.

Do not silently fix them as part of the extraction.

After the behavior-neutral move is complete and protected, handle each confirmed defect as a separate reviewed slice with migration and compatibility analysis where required.

A content-safety field missing from persisted post state is not a cosmetic cleanup.

Treat persistence changes with the appropriate seriousness.

## 8. Define retention policies instead of leaving immortal maps

The audit found application-lifetime maps with no eviction or removal policy.

Recheck each current owner.

Examples found by the exploration include:

- emoji URL locks;
- direct-message cached last posts;
- Misskey thread continuation state;
- pooled HTTP clients.

Do not create one generic cache abstraction for unrelated owners.

Each structure needs a policy that matches what it stores.

For each current unbounded structure, decide and implement one of:

- explicit removal when the owning operation ends;
- account/session teardown;
- bounded LRU or count limit;
- time-based expiry;
- weak ownership where semantically correct;
- another explicit, tested retention rule.

Measure or write stress tests where memory impact cannot be established from inspection alone.

Do not claim a memory leak solely from map growth without evidence.

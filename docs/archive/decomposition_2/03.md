# Exploration task: remove external-link handling from post display

## Scope

Investigate external URL opening in the current Beeline codebase and produce a small refactor plan that removes generic browser-launch behavior from `PostRow.kt`.

This is an exploration task. Do not change application code. Do not create additional subagents.

The current checkout is authoritative. The v0.2.1 code is historical context only.

## Problem

A generic `openExternal` function was placed in `PostRow.kt`.

Opening a URL in the system browser is not post-row presentation logic. Other files also depend on this function, which makes a post UI file an owner of unrelated application behavior.

In v0.2.1, Beeline already had an `ExternalLinkHandler` under the UI link package, but that handler delegated browser opening back to the function owned by `PostRow.kt`. Confirm the current structure before proposing a fix.

## Investigation

Find every current call to:

- `openExternal`;
- `ExternalLinkHandler`;
- direct `ACTION_VIEW` browser intents used for normal external links;
- tracking-parameter cleanup used before external navigation.

Map which callers need generic external navigation and which callers have feature-specific behavior.

Determine the correct owner for:

- URL preparation;
- optional tracking-parameter cleanup;
- null and blank URL handling;
- creation of the browser intent;
- failure handling when no activity can open the URL.

Prefer the existing link/navigation utility area if it still exists and still fits the responsibility.

Do not create a new abstraction when an existing focused owner can do the job.

## Requirements

After the refactor, generic external-link code must not depend on post-display code.

`PostRow.kt` must call the generic link owner like any other caller.

Other screens must import the generic owner from its proper package.

Preserve current user behavior:

- valid external URLs open in the browser or matching system handler;
- blank or absent URLs do nothing if that is current behavior;
- tracking-parameter cleanup still follows the user setting;
- failures remain safe and do not crash the app.

Check whether the historical design prepares a URL more than once. If it does, report it and define one clear preparation point.

Do not expand this task into deep-link routing, in-app browser work, or navigation redesign.

## Verification

Identify existing tests for tracking cleanup and external-link handling.

Define the smallest additional tests needed to protect the extracted behavior.

Search for stale imports after the move.

Confirm that no generic link utility imports `PostRow.kt`, the post package, or another feature-specific UI owner.

## Required output

Return one Markdown report in the project writing style.

Use these sections:

1. `Current ownership`
2. `Current callers`
3. `Correct owner`
4. `Behavior that must stay unchanged`
5. `Import and dependency cleanup`
6. `Refactor order`
7. `Verification`
8. `Risks and open questions`

Keep this refactor small. Do not mix it with unrelated post-row decomposition.

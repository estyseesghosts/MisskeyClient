# Exploration task: reduce the Beeline app dependency surface

## Scope

Investigate the current Beeline codebase and produce a refactor plan for the dependency surface around `PalustrisApp.kt`, `ConnectedApp.kt`, and the tests that construct the app.

This is an exploration task. Do not change application code. Do not create additional subagents.

The current checkout is authoritative. The v0.2.1 code is historical context only. Confirm all file names, symbols, call sites, and ownership boundaries against the current checkout before you make a recommendation.

## Problem

The app entry point has accumulated a very large parameter list. Adding a feature can require the same new dependency or callback to pass through `ConnectedApp.kt`, `PalustrisApp.kt`, and many tests.

That structure is not acceptable for long-term maintenance.

The v0.2.1 code also contains many temporary-looking import aliases around moved app-shell functions. Determine whether those aliases still exist and whether they still serve a useful purpose.

Do not solve the problem by placing every existing parameter into one large data class. That would hide the same coupling behind one object.

## Investigation

Map the current construction path from the Android entry point to the connected app shell and then to `PalustrisApp`.

For each major parameter or dependency group, identify:

- who creates it;
- who owns its lifecycle;
- who reads it;
- who mutates it;
- whether it is application state, UI state, a service, a repository, a controller, an action, or configuration;
- whether it must cross the `PalustrisApp` boundary at all.

Look for parameters that travel through a layer without being used there.

Look for callback groups that represent one logical responsibility but are passed as many unrelated lambdas.

Look for repositories or services that are passed directly into broad UI layers when a narrower owner could expose the required state and actions.

Review the tests that construct `PalustrisApp`. Determine why they need to know so much about app-wide construction.

Review the current dependency-injection structure before proposing a new one. Prefer the smallest design that gives clear ownership. Do not introduce a new framework only to reduce a function signature.

## Design requirements

The final design must make feature work local.

A normal feature must not require unrelated edits across the app entry point, connected shell, and many tests only to pass one more parameter through the stack.

Group values only when they share a real lifecycle or responsibility. Suitable groups can include state plus actions for one feature area, or a small set of services with one owner. Do not create generic bags such as `AppDependencies`, `EverythingState`, or equivalent objects that become new dumping grounds.

Keep immutable state separate from long-lived services where that improves ownership.

Keep UI presentation state separate from data-layer dependencies where that improves ownership.

Preserve Compose state behavior. Avoid changes that create unstable objects, excessive recomposition, hidden mutable state, or lifecycle leaks.

Make tests easier to construct. Explore focused test fixtures, narrow interfaces, defaults that are safe for tests, or other patterns that remove the need for every test to understand the whole app.

Clean up obsolete import aliases. Keep an alias only when it resolves a real naming conflict or makes ownership clearer.

## Risks to examine

Call out risks before the related refactor step.

At minimum, inspect:

- state ownership changes;
- Compose stability and recomposition;
- callback capture and stale-state risks;
- lifecycle ownership;
- account switching;
- initial-route handling;
- test behavior that depends on current construction details;
- dependency cycles;
- accidental creation of a new god object.

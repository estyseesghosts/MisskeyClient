# Exploration task: design the Beeline documentation foundation

## Scope

Design a documentation system that can be introduced while the Beeline refactor is finalized.

This is an exploration task. Do not change application code. Do not create additional subagents.

The current checkout is authoritative. Review the existing README, project writing guide, work logs, code comments, tests, and any documentation added after v0.2.1 before you propose new structure.

The documentation must serve three different needs:

- useful comments and KDoc close to the code;
- a human-facing project wiki;
- a separate agent-facing wiki.

The agent-facing wiki must follow the project writing guide.

Documentation maintenance must become part of normal development, not a one-time cleanup.

## Goals

A human contributor should be able to understand the major architecture, build and test Beeline, find the owner of a feature, and understand important compatibility rules without reading the whole repository.

An agent should be able to locate the correct subsystem, understand ownership and invariants, identify required tests, and avoid repeating old architectural mistakes.

Code comments should explain non-obvious intent, invariants, compatibility constraints, lifecycle rules, and reasons for unusual decisions.

Comments must not restate obvious Kotlin syntax.

## Existing material

Audit the current documentation before adding new sources of truth.

Identify what belongs in:

- the README;
- a human wiki;
- an agent wiki;
- code comments or KDoc;
- work logs;
- generated or reference documentation.

Find stale, duplicated, contradictory, or temporary information.

Do not preserve a document only because it already exists.

Do not move short-lived task history into permanent architecture documentation.

## Human wiki

Propose a small initial page set.

Cover the information a human maintainer or contributor needs first. Likely areas include:

- project overview and supported server families;
- architecture and module boundaries;
- account and session model;
- protocol abstraction;
- data storage and migrations;
- notifications and push;
- UI and navigation;
- media handling;
- build, test, and release workflow;
- troubleshooting;
- contribution and documentation rules.

Adjust this list to the current codebase. Do not create pages with no useful content only to complete a template.

Keep user-facing product documentation separate from internal implementation detail where practical.

## Agent wiki

The agent wiki is an engineering map, not a second README.

Design pages that answer questions such as:

- Where does this behavior belong?
- Which layer owns this state?
- Which files form this subsystem?
- Which invariants must not change?
- Which protocol differences matter?
- Which tests must run after this type of change?
- Which persistence formats require backward compatibility?
- Which areas are fragile or easy to misuse?
- Which historical names are internal only?
- What must an agent update when behavior or ownership changes?

Include a clear `where to change X` map for common feature areas.

Include cross-cutting rules for multi-account isolation, lifecycle ownership, error handling, persistence compatibility, protocol boundaries, UI state, and testing.

Do not turn the agent wiki into a copy of source code. Link to authoritative code and tests instead.

## Code comments and KDoc

Define when comments are required.

Prefer comments for:

- reasons that are not clear from code;
- compatibility behavior;
- concurrency and lifecycle invariants;
- persistence format constraints;
- protocol quirks;
- intentionally unusual fallbacks;
- non-obvious performance tradeoffs.

Prefer KDoc for APIs whose contract is not obvious from the type signature.

Do not require comments on every class or function.

Remove or update comments when the code makes them false.

## Source of truth and wiki drift

A wiki can drift away from the repository.

Propose a clear source-of-truth policy.

Evaluate whether wiki source should also live in the main repository and be published or synchronized to the wiki. If the project should keep wiki pages only in the wiki repository, define how code changes will force the matching documentation review.

Do not create two independently edited copies of the same architecture text without a maintenance rule.

## Maintenance rules

Documentation must be part of the definition of done.

Propose a lightweight rule set so that a change updates documentation in the same work slice when it changes:

- behavior;
- ownership;
- architecture;
- persistence;
- protocol support;
- build or release steps;
- test requirements;
- a known invariant.

Include a review checklist that agents and humans can follow.

Keep maintenance proportional. Small implementation changes that do not alter documented behavior should not require meaningless documentation edits.

## Refactor integration

Show when documentation should be written during the remaining refactor.

Do not fully document an ownership model immediately before it is replaced.

Document stable boundaries as they are finalized.

For risky refactors, write the invariant and verification notes before or with the implementation so later work has a contract to preserve.

Return one Markdown report in the project writing style.

Use these sections:

For each proposed wiki page, state its purpose and the information that belongs there.

Keep the first version small enough to maintain.

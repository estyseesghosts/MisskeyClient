# App Dependency Surface Review

## 1. Current shape

The current construction path has three layers.

- `MainActivity.kt:29-63` is the Android composition root. Hilt creates `AccountManager` as an activity ViewModel. Hilt injects `SocialSourceFactory`, `AccountSourceRegistry`, `DraftStore`, `NotificationLaunchRouter`, `ForegroundNotificationStreamController`, `AppPreferencesRepository`, and `PostPreferencesRepository` into the activity.
- `MainActivity.onCreate` handles the initial intent before it calls `setContent`. It then passes all eight dependencies to `ConnectedApp` as positional arguments (`MainActivity.kt:52-63`).
- `ConnectedApp.kt:89-98` receives those eight values. It collects account state, account references, active-session state, application preferences, post preferences, and pending notification launches.
- `ConnectedApp.kt:114-115` resolves one shared `SocialSource` from `AccountSourceRegistry` or creates one through `SocialSourceFactory`.
- `ConnectedApp.kt:118-135` owns the foreground lifecycle bridge for `NotificationStreamController`.
- `ConnectedApp.kt:137-197`, `224-297` creates the account-scoped assisted ViewModels and collects their state. The models are `FeedViewModel`, `NotificationsViewModel`, `DirectMessageViewModel`, two `SavedPostsViewModel` instances, two `NotificationSettingsViewModel` instances, `ModerationViewModel`, `ProfileViewModel`, `PostThreadViewModel`, and `EmojiCatalogViewModel`.
- The ViewModel keys include the account ID and `SessionUi.sessionGeneration` (`ConnectedApp.kt:138-193`, `224-290`). The source-backed models also receive the durable `Session.sessionRevision` where post ownership requires it.
- `ConnectedApp.kt:199-204`, `240-283`, and `295-296` stops selected models when the connected session changes or the composition leaves the screen.
- `ConnectedApp.kt:364-480` flattens all collected state and model operations into the `PalustrisApp` call. It also contains the cross-surface post update and publish fan-out.
- `ConnectedApp.kt:484-533` separately owns the settings host, application preference updates, selected notification-account state, and moderation state.
- `PalustrisApp.kt:158-257` accepts 98 parameters. The list contains identity, session identity, UI state, services, configuration, and callbacks for nine feature areas.
- `PalustrisApp.kt:258-1490` owns navigation state, overlay state, composer state, profile-editor state, selected-post state, media-transition state, post-action state, and the final presentation tree.
- The destination wrappers already exist. `AppHomeDestinationContent.kt`, `AppSearchDestinationContent.kt`, `AppPhotoGridDestinationContent.kt`, `AppNotificationsDestinationContent.kt`, `AppProfileDestinationContent.kt`, `AppLocalPageContent.kt`, and `AppLargeDetailPane.kt` narrow the leaf screen calls, but `PalustrisApp` still assembles every wrapper.

`AccountManager` is the lifecycle owner for account and session state. `AccountManager.kt:102-140` restores sessions, `273-333` switches and removes accounts, and `364-376` publishes a new active session and registers its notification source. It also owns account-scoped removal of post preferences, Photo Grid preferences, direct-message data, emoji data, and push-related state.

`NotificationSyncOrchestrator` is the application/account lifetime owner for notification synchronization (`NotificationSyncOrchestrator.kt:79-179`). It owns the registry generation used by `AccountSourceRegistry`. `ForegroundNotificationStreamController` owns live sockets only while the active account is foregrounded (`ForegroundNotificationStreamController.kt:32-118`). These services must not move into a Compose screen or a screen-lifetime ViewModel.

The current feature inputs have these owners.

| Area | Current values | Current creator and owner | Current consumer or mutator |
| --- | --- | --- | --- |
| Account identity | `account`, `accounts`, `onSwitchAccount`, `onAddAccount`, `onSignOut`, `onOpenSettings` | `AccountManager` creates account state. `ConnectedApp` reads it. | `PalustrisApp` uses it for account selection, profile identity, sign-out, and settings entry. |
| Session identity | `sessionGeneration`, `sessionRevision` | `AccountManager` creates both. The generation is runtime state. The revision is persisted in `Session`. | `ConnectedApp` keys ViewModels. `PalustrisApp` keys remembered owners and passes revision to post screens. |
| Source access | `actionSource` | `ConnectedApp` resolves a source from the application registry. | `PalustrisApp` gives it only to `PostActionOwner`. |
| Home and search data | `feedState`, `ownedPosts`, search callbacks, timeline callbacks | `FeedViewModel` owns feed, account search, timeline, publish, and Photo Grid operations. | `PalustrisApp` routes the state to Home, Search, notification details, profile posts, local pages, and detail panes. |
| Photo Grid | `photoGridFeed` and six Photo Grid callbacks | `PhotoGridController` inside `FeedViewModel` owns this state. | Search presentation consumes it. The state must remain separate from Home navigation state. |
| Profile | `profileState` and profile callbacks | `ProfileViewModel` owns target, timeline pages, relationships, and profile editing. | Profile presentation consumes the state. `PostActionOwner` also calls `onRefreshProfile` after a relationship mutation. |
| Thread | `threadState` and eight thread callbacks | `PostThreadViewModel` owns acquisition, foreground behavior, and thread mutations. | `PalustrisApp` activates it from selected-post state and sends updates back to other models. |
| Saved collections | `savedPostsState`, `likedPostsState`, and collection callbacks | Two keyed `SavedPostsViewModel` instances own bookmarks and likes. | Local-page presentation consumes each collection. |
| Notifications | `notificationState`, notification actions, and `initialNotificationRoute` | `NotificationsViewModel` owns inbox state. `NotificationLaunchRouter` owns the pending launch. | Notification presentation consumes both state and route. |
| Direct messages | `directMessageState` and direct-message callbacks | `DirectMessageViewModel` owns the repository-backed inbox and conversation state. | The Notifications destination switches to direct-message presentation. |
| Emoji | `emojiCatalogState`, `emojiCapabilities`, and picker callbacks | `EmojiCatalogViewModel` owns the catalog and picker preferences. The source owns emoji capabilities. | The global reaction bubble and composer picker consume them. |
| Composer | `draftStore`, `postPreferences`, `onPublish`, and composer-local state | `DraftStore` is a data-layer service. `PalustrisApp` owns draft text, warning, audience, reply, quote, and save state. | Composer and draft-page UI consume the state. |
| Presentation policy | `contentWarningRules` | `ConnectedApp` derives it from application and account post preferences. Existing composition locals also expose the same policy. | `PalustrisApp` forwards it to destination wrappers and detail screens. |
| Settings | application preference repository and settings callbacks in `ConnectedApp` | `ConnectedApp` directly updates `AppPreferencesRepository` and `PostPreferencesRepository`. | `SettingsHost` and notification settings presentation consume the values. |

The source and session ownership is already mostly outside Compose. The main dependency problem is the adapter layer between those owners and `PalustrisApp`, not the Hilt bindings themselves.

## 2. Coupling that should be removed

`ConnectedApp` is both a lifecycle host and a feature coordinator. It creates eleven model slots, collects their state, installs lifecycle effects, wires cross-model projections, owns notification launch handling, and renders settings. A new feature currently requires edits to this coordinator and to the 98-parameter `PalustrisApp` call.

`PalustrisApp` is both a navigation shell and a feature integration boundary. It owns the correct presentation state for navigation, overlays, selected posts, and saved-state restoration. It should not also receive every repository-backed state and every ViewModel operation as separate arguments.

The cross-surface post fan-out is a separate responsibility.

- `ConnectedApp.kt:243-264` registers a thread update listener and forwards each update to feed, saved posts, liked posts, profile, and notifications.
- `ConnectedApp.kt:386-396` forwards a published post to feed, saved posts, liked posts, profile, notifications, and thread state.
- The same fan-out is repeated in different forms for external post updates and published replies.

This logic should have one focused owner. It is not a generic dependency container. It is a projection coordinator that knows which account-scoped model owners receive a normalized post update.

Feature callbacks are also flattened.

- Home timeline refresh and load-more actions are separate from Photo Grid refresh, selection, hashtag, and preference-error actions.
- Profile browsing, relationship actions, profile editing, and profile-page navigation are all separate responsibilities.
- Notifications and direct messages share a destination but have different state owners and different lifecycles.
- Bookmarks and likes use the same ViewModel class but have different mutations and capability behavior.
- The global post callbacks are shared by many screens, while reaction callbacks for saved posts, liked posts, profile posts, and thread posts target different owners.

Passing these callbacks as a flat list hides which owner handles a mutation. It also makes callback capture harder to review.

`actionSource` is a service dependency in a broad UI signature. `PalustrisApp.kt:261-263` passes it only to `PostActionOwner`, which owns relationship and report requests. The source must not be visible to the full navigation shell.

`draftStore` is a data-layer service in a broad UI signature. `PalustrisApp.kt:272` creates a `PreferencesDraftStore` fallback inside the Compose function when no store is supplied. This fallback keeps direct previews and tests simple, but it also puts storage selection, a SharedPreferences name, migration, and account-scoped draft operations inside the app shell.

`ownedPosts` duplicates data already in `FeedState.ownedPosts`. Production passes the same list at `ConnectedApp.kt:410`. `PalustrisApp.kt:773-784` uses the separate value only when resolving a selected post, and `PalustrisApp.kt:921` uses it as the Home fallback. This is a second source of truth for the same feed-owned data.

`contentWarningRules` is derived in `ConnectedApp.kt:372` and is then forwarded through several wrappers. The existing `LocalContentWarningRules`, `LocalMutedHashtags`, and `LocalHiddenContentPresentation` providers are installed at `ConnectedApp.kt:331-336`. The leaf screens already default to these locals. The shell therefore carries one presentation policy both as explicit arguments and as composition-local state.

Notification settings are wired twice. `ConnectedApp.kt:175-186` creates a model for the active account, while `181-186` creates another model for the account selected in settings. `ConnectedApp.kt:441-455` sends the active-account model through `PalustrisApp`, and `ConnectedApp.kt:507-518` sends the settings-route model through `SettingsHost`. A refactor must keep these account identities distinct. It should not solve the duplication by sharing one active-account object with settings for another account.

The tests reveal the same coupling. Most app-shell tests replace the activity content and construct `PalustrisApp` directly. They must know which state and callback names the 98-parameter function accepts, even though they are testing presentation and navigation rather than production dependency construction.

## 3. Proposed ownership boundaries

Keep `MainActivity` as the Android entry point. Its activity-specific work should remain intent dispatch, locale handling, refresh-rate handling, and lifecycle setup. It should not become the owner of feature state.

Make `ConnectedApp` a composition host with focused owners rather than a value-forwarding layer.

- An account-session owner should read `AccountManager.activeSession` and `AccountManager.session` and create the source-backed feature owners for the current account.
- A separate post-projection owner should connect feed, saved, liked, profile, notification, and thread update sinks. It should validate account and session revision before forwarding updates.
- A separate settings owner should own application preference updates, account-selected notification settings, moderation state, and post-preference updates.
- A notification-launch handoff should convert `NotificationLaunchRouter` output into one shell navigation input after account selection. It should not expose the router or its storage to presentation components.
- Foreground stream start and stop should remain in the existing `NotificationStreamController` boundary. The owner that invokes it must remain scoped to the activity-connected account, not to an individual destination.

Use existing Hilt bindings. Do not add another dependency-injection framework. The focused owners can be Hilt-created services or narrowly scoped state holders. They must not form a cycle with `AccountManager`; `AccountManager` remains the authority for account switching, session replacement, and account removal.

Give `PalustrisApp` a small shell contract and one feature contract per independent presentation area. A contract can contain immutable state plus actions for one feature responsibility. It must not contain repositories, access tokens, `SocialSource`, ViewModels, or unrelated feature state.

Keep the following state in the shell.

- Destination, search panel, notification panel, local page, overlay, selected post, selected post origin, and notification route.
- Scroll states and saveable navigation state.
- Media transition registry and post-action bubble presentation state.
- The current account identity needed for visible navigation and profile selection.

Keep the following state outside the shell.

- Feed, notification, direct-message, saved-post, profile, thread, emoji, moderation, and notification-settings state.
- Draft persistence and account-scoped post preferences.
- Session tokens, source instances, repository instances, synchronization jobs, and stream jobs.

Keep UI policy separate from services. `PostPreferences`, `ContentWarningRules`, emoji capabilities, and account/session identity are values. `DraftStore`, `SocialSource`, repositories, controllers, and ViewModels are services or owners. A feature contract should not merge these categories merely to reduce the number of parameters.

The current `AppShellState.kt` is a suitable home for shell enums and pure navigation helpers. It should not become a general state bag. Add a focused shell state holder only when it owns a real navigation responsibility.

## 4. Parameter groups worth creating

The following groups are justified because each one has one owner and one presentation responsibility. The names describe responsibilities, not required final class names.

| Group | Values | Why the values belong together |
| --- | --- | --- |
| Account switcher | `accounts`, `onSwitchAccount`, `onAddAccount`, `onOpenSettings`, `onSignOut` | `AppSelectionSheet` reads the account list and invokes account-level actions. These actions share `AccountManager` ownership and the account-switcher lifecycle. |
| Connected account context | `account`, a runtime session key, and a durable session revision | The active account and the two revisions identify one connected presentation generation. The runtime generation controls ViewModel and remembered-owner replacement. The durable revision rejects stale post callbacks. Keep the revision distinct from the runtime generation inside the focused owner. Do not expose the session token. |
| Home feed | `FeedState`, timeline refresh, timeline load-more, and Home post actions | `FeedViewModel` owns the Home feed and its timeline requests. The group keeps Home actions beside the state they mutate. Do not put Photo Grid state in this group. |
| Search | account-search state, search submit, and search pagination actions | Account search has its own query and pagination behavior, even though the current `AccountSearchState` is nested in `FeedState`. The presentation contract can keep the current model until a separate feed-state split is approved. |
| Photo Grid | `PhotoGridFeedState`, ensure-loaded, feed selection, refresh, load-more, hashtag, and preference-error actions | Photo Grid has independent state and timeline selection by project rule. Its actions all target `PhotoGridController`, so they have one lifecycle and one owner. |
| Profile | `ProfileUiState`, profile loading, category, relationship, and editor actions | `ProfileViewModel` owns the selected profile, relationship state, profile pages, and editor requests. Profile navigation actions such as opening a profile or profile image should remain shell actions, not ViewModel services. |
| Thread detail | `PostThreadUiState` and thread acquisition and mutation actions | `PostThreadViewModel` owns the selected thread session, foreground behavior, continuation, refresh, and thread mutations. The group should carry the thread contract without carrying other feed models. |
| Bookmarks collection | bookmark `SavedPostsUiState` and bookmark refresh, pagination, unsave, permission, and reaction actions | Bookmark actions mutate the bookmark collection. They should not be mixed with likes simply because both use `SavedPostsViewModel`. |
| Likes collection | likes `SavedPostsUiState` and likes refresh, pagination, favourite, and reaction actions | Likes have different capability and removal behavior from bookmarks. A separate contract makes that difference visible. |
| Notifications | `NotificationsUiState` and notification refresh, pagination, acknowledgement, dismissal, follow-request, and query actions | `NotificationsViewModel` owns the inbox state and all inbox mutations. The pending launch route is a shell handoff, not part of this state group. |
| Direct messages | `DirectMessageUiState` and conversation, refresh, pagination, open, back, start, and send actions | `DirectMessageViewModel` owns the direct-message repository and conversation state. The group remains separate from notification state despite the shared destination. |
| Emoji picker | `EmojiCatalogState`, `EmojiCapabilities`, and catalog and picker-preference actions | The catalog ViewModel owns loading and picker preferences. Capabilities are read-only source-backed configuration used by the picker and reaction bubble. Keep this group separate from post mutation services. |
| Composer and drafts | composer state/actions plus a narrow draft owner | Composer text, warning, audience, reply, quote, draft save, and publish behavior form one presentation responsibility. The narrow owner may depend on `DraftStore`, but `DraftStore` must not cross into `PalustrisApp`. |
| Post action host | a narrow relationship/report action owner or interface and its refresh notification | `PostActionOwner` already owns one popup and account-scoped relationship requests (`PostActionOwner.kt:47-176`). Keep its source and coroutine scope inside that owner. Expose only popup state and actions to presentation. |
| Notification settings | one per selected account, with `NotificationSettingsUiState` and its setting actions | Both the active-account overlay and the settings route use the same responsibility, but each must retain its selected account identity. The owner should provide a focused per-account contract rather than a shared global settings bag. |

These groups should be separate values or narrow interfaces. Do not create `AppDependencies`, `EverythingState`, or an equivalent object containing all rows of this table. A feature should update its own contract and owner without editing unrelated contracts.

## 5. Parameters that should disappear from the boundary

The following values can leave the `PalustrisApp` parameter list after the related owner exists.

- `onOpenReactionPicker` is a confirmed dead parameter at `PalustrisApp.kt:209`. The function body never reads it. The shell passes `::expandReactionPicker` directly to child wrappers at `PalustrisApp.kt:904` and `929`. Remove this parameter from `PalustrisApp` first, then remove its forwarding from the app-shell wrappers when their leaf APIs no longer need it. Direct `HomeFeed` and `SavedPostsScreen` tests can continue to test their own picker callback if those leaf contracts still support it.
- `ownedPosts` duplicates `feedState.ownedPosts`. Production passes `feed.ownedPosts` separately at `ConnectedApp.kt:410`. Derive selected-post candidates from the feature contracts or make one feed contract own the list. Update the account-switching test fixture before removing the parameter. Do not silently choose a second list when the two values differ.
- `actionSource` should disappear from `PalustrisApp`. It is used only to construct `PostActionOwner` at `PalustrisApp.kt:261-263`. Create the post-action owner in a focused host and expose only its presentation state and actions.
- `draftStore` should disappear from `PalustrisApp`. Move draft listing, saving, deleting, and legacy migration behind a composer or draft owner. Keep `EncryptedDraftStore` in the data layer. Inject `InMemoryDraftStore` or an explicit persistence fixture in tests instead of selecting `PreferencesDraftStore` from inside the production UI function.
- `sessionGeneration` should not remain a general feature input. A connected-session host can use it to key the feature owners and can key the `PalustrisApp` instance when a session replacement must reset shell state. Do not delete the generation until reauthentication for the same account has an explicit state-restoration decision.
- `contentWarningRules` can disappear from the `PalustrisApp` boundary if the existing `LocalContentWarningRules`, `LocalMutedHashtags`, and `LocalHiddenContentPresentation` providers remain the single presentation-policy boundary. The leaf defaults already read those locals. If explicit leaf contracts remain preferred, keep the value in a feature presentation contract rather than as a top-level shell parameter.
- `postPreferences` should move into the composer and settings contracts. `PalustrisApp.kt:494-522` uses it for audience policy and `ConnectedApp.kt:501-532` uses it for settings. It does not belong beside navigation state or source services.
- `emojiCapabilities` and emoji catalog callbacks should move into the emoji picker and post-action host. The top-level shell should not know the source capability object merely to render a picker.
- `notificationSettingsState` and the notification-settings callbacks should move into the focused notification-settings contract. The shell should request the overlay and render that contract without carrying eleven individual settings actions.
- `onReply` is not supplied by production `ConnectedApp`; its production default is a no-op. It exists as a test observer in `HomeFeedTest.kt:702` and `SignInScreenTest.kt:152`, while the real composer behavior comes from `handleReply` at `PalustrisApp.kt:561-564`. Replace those test observers with assertions on the composer or a test-only interaction recorder before removing the production parameter.

The following values must not disappear without an explicit replacement.

- `account` remains shell identity and is needed by profile, composer, account selection, and account-specific action checks.
- `sessionRevision` remains necessary wherever `OwnedPost` ownership and stale-session rejection are checked. It should move into a narrow account/post context, not be dropped.
- `initialNotificationRoute` remains a one-shot shell navigation input. It should not be folded into `NotificationsUiState` because launch routing and inbox data have different owners.
- `onOpenSettings` remains a shell navigation action, but it belongs inside the account switcher contract rather than the full parameter list.
- Feature state such as `feedState`, `profileState`, `threadState`, and `notificationState` remains necessary. The change is to place each value with its owner and actions, not to hide it in one object.

## 7. Test construction plan

No current test constructs `ConnectedApp` directly. The tests construct `PalustrisApp` directly or use a leaf screen.

- `HomeFeedTest.kt:54-69` has a reusable `show` helper that supplies an account, feed state, and one reaction callback. The same file also constructs `PalustrisApp` directly for profile, thread, search, hashtag, and reaction cases (`HomeFeedTest.kt:122-133`, `248-263`, `568-580`, `606-622`, `773-918`).
- `NavigationTest.kt:60` installs a no-argument `PalustrisApp` before each test. It then replaces content with focused account, feed, notification, profile, and account-switching states (`NavigationTest.kt:265-268`, `365-377`, `393-407`, `437-441`, `474-475`, `535-559`, `593-599`, `620-631`, `727-728`, `829-830`, `847-848`, `873-874`, `900-909`).
- `SignInScreenTest.kt` uses direct app construction for content warnings, sensitive media, publishing, account switching, and post action behavior (`SignInScreenTest.kt:49-73`, `85-91`, `126-155`, `191-206`, `252-263`, `294-304`).
- `ReplyComposerTest.kt:50-58` supplies only feed state to exercise the reply composer.
- `SearchPanelRestorationTest.kt:25` uses no-argument `PalustrisApp` with `createComposeRule` and tests saveable Search panel state.
- `WideNavigationTest.kt:54` installs the no-argument shell, while `WideNavigationTest.kt:119-127` supplies a focused large-detail state.
- `Api29StartupInstrumentedTest.kt:53` supplies an account and feed state to the real activity for API 29 media behavior.

Use a test-only fixture builder or focused test helpers. The fixture must not be a production `AppDependencies` object.

- Provide safe empty feature contracts and explicit no-op actions for tests that only need navigation chrome.
- Provide focused helpers such as `showFeed`, `showProfile`, `showNotifications`, and `showThread`. Each helper should accept only the state and action recorders relevant to that scenario.
- Keep action recorders in test code. A recorder can capture a selected post or account without requiring a production callback solely for test observation.
- Provide `InMemoryDraftStore` explicitly for deterministic composer tests. Use a separate persistence fixture for `NavigationTest` draft recreation coverage. Do not make a production Compose default choose a SharedPreferences implementation.
- Keep direct leaf tests for `HomeFeed`, `ProfileScreen`, `SearchScreen`, notification screens, and other extracted components. These tests should not construct the connected account graph.
- Keep `createAndroidComposeRule<MainActivity>` for tests that verify window insets, system bars, activity recreation, API compatibility, or real Hilt startup. Use `createComposeRule` for shell-only restoration tests when an Android activity is not required.

The fixture should make the production construction invisible to most presentation tests. A test for one feature should not edit `MainActivity`, `ConnectedApp`, and unrelated feature arguments when a new action is added.

Preserve the existing high-value scenarios during the move.

- Account switching must rebind the displayed feed, post ownership, navigation, profile target, and source-scoped actions (`SignInScreenTest.kt:166-219`, `NavigationTest.kt:887-920`).
- Reauthentication and session replacement must not accept an old `OwnedPost` callback. The durable `sessionRevision` check must remain active.
- Notification launch handling must select an existing account, handle an unavailable account, and render the correct route after the active session changes.
- Initial route handling must not lose a pending launch during startup or clear it before the target account is ready.
- Drafts must remain account-scoped and survive the existing activity recreation path (`NavigationTest.kt:757-776`).
- Compact and wide navigation, thread detail, notification detail, Photo Grid, and reaction-bubble behavior must retain their existing presentation tests.

## 8. Refactor order

1. Record current contracts with characterization tests and a complete symbol map. Risk: a signature move can hide an existing callback difference or an account/session identity assumption.
2. Remove the confirmed dead `onOpenReactionPicker` parameter from `PalustrisApp` and its app-shell wrappers. Risk: leaf screens still use similarly named callbacks, so search and update only the shell forwarding path.
3. Introduce focused feature contracts with safe test defaults. Start with account switching, Home, Profile, Thread, Notifications, Direct Messages, collections, Photo Grid, Search, Emoji, and Composer. Risk: freshly allocated contract objects can cause recomposition or stale callback behavior. Keep values immutable, construct long-lived owners once, and use `rememberUpdatedState` or equivalent owner updates when callbacks change.
4. Move `PostActionOwner` creation and `DraftStore` use behind focused hosts. Risk: moving a coroutine scope or owner across a composition boundary can leak work or retain an old account. Key owners by account ID and session generation or revision, dismiss them on replacement, and keep storage account-scoped.
5. Move cross-model post update and publish fan-out into one projection coordinator. Risk: a god object can replace the current god function. Limit the coordinator to normalized post projections, registered sinks, account checks, and session-revision checks. Keep navigation and UI state outside it.
6. Extract the account-session feature host from `ConnectedApp`. Risk: creating a new source during recomposition can give models and notification streams different source instances. Resolve the registry-owned source once per account/session generation and preserve `AccountSourceRegistry` as the application source authority.
7. Extract the settings feature host from `ConnectedApp`. Risk: active-account notification settings and settings-route notification settings can target different accounts. Keep a keyed per-account owner for each route and retain the existing selected-account behavior.
8. Change `PalustrisApp` to receive the focused shell and feature contracts. Keep navigation state and overlay state in the shell. Do not pass ViewModels, repositories, `SocialSource`, or a token through the boundary.
9. Reduce `MainActivity` and `ConnectedApp` construction to the focused production owners. Use existing Hilt bindings. Risk: injecting a coordinator that depends on `AccountManager` while `AccountManager` depends on that coordinator creates a cycle. Keep account lifecycle ownership one-directional.
10. Replace direct test call sites with focused fixture helpers. Migrate test-only `onReply` observers to visible composer assertions or test recorders. Keep explicit state for tests that verify account switching, initial routes, process recreation, insets, or session behavior.
11. Replace the `moved` aliases with direct imports and remove the two unused imports. Risk: a broad rename could affect unrelated `movedTo` protocol model fields. Restrict the search to the alias names and imports in `PalustrisApp.kt`.
12. Run focused tests and static searches before the full required build. Review the diff for unchanged account ownership, source identity, callback routing, Compose keys, and saveable state behavior.

This examination made no application or test-code changes. No Gradle, device, or live-server verification was run for this report.

## 10. Risks and open questions

- Compose stability is the main implementation risk. Grouped values must remain immutable. Stable action owners must not be recreated on every recomposition. Remember keys must include the account and the required session identity.
- Callback capture can become stale when a feature model changes but a remembered owner does not. Review `PostActionOwner` and all projection callbacks. Use a current-callback mechanism instead of adding every lambda to a remember key.
- Account switching is asynchronous. `ConnectedApp.kt:311-323` switches the receiving account and sets `initialNotificationRoute` in the same effect. Preserve the current route behavior, and test the case where the switch has not completed when the route first renders.
- The current top-level app key is only `state.account!!.id` (`ConnectedApp.kt:364`). A session replacement for the same account can therefore retain shell state while model keys include a new `sessionGeneration`. Decide whether same-account reauthentication should preserve navigation or reset it before changing the key.
- Source lifecycle is application-scoped through `NotificationSyncOrchestrator` and `AccountSourceRegistry`. A new owner must not create an unregistered replacement source for a feature or allow a stale source to receive current-session actions.
- Notification stream start and stop must remain tied to the connected account and activity lifecycle. Moving stream control into a destination owner could stop delivery when the user changes screens.
- Notification settings can represent the active account or another account selected in Settings. A single mutable settings contract without an account key could apply an action to the wrong account.
- A projection coordinator can become a new god object if it starts owning navigation, drafts, preferences, or screen state. Keep its API limited to normalized post update sinks and explicit publication results.
- Moving `DraftStore` out of Compose must preserve legacy draft migration and account-scoped deletion. The current fallback uses the SharedPreferences name `local_draft`, while `EncryptedDraftStore` uses no-backup encrypted files. These are different persistence contracts.
- Tests currently use both production activity startup and direct shell replacement. A fixture change must not remove coverage for Hilt startup, window insets, activity recreation, or API 29 behavior.
- `onReply` has test-only observers today. Decide whether those tests should assert the composer result or whether a test-only action recorder remains useful. Do not keep a production parameter only because two tests inspect an internal event.
- The current `contentWarningRules` explicit argument and composition-local policy can diverge if both remain writable. Select one presentation-policy owner before removing one path.
- The final design must keep protocol behavior behind `SocialSource` and adapter boundaries. The dependency refactor must not add Misskey or Mastodon branches to generic shell contracts.

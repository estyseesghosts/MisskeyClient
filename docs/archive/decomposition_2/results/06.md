# Beeline Structural And Bug Audit

## Executive summary

The current checkout fixes several findings from the earlier decomposition review.

This audit found three new correctness defects:

- `FeedViewModel` can publish a cancelled paging response after refresh.
- `DirectMessageViewModel` can publish a response for a conversation that the user no longer selected.
- `MastodonCapabilityProbe` treats a missing sentinel status as proof that emoji reactions are unsupported.

The audit also found a medium retention risk. Several application-lifetime maps have no eviction or removal policy.

No application code or tests changed. No live server or physical device test ran.

## New correctness findings

### Medium: Feed paging can append a response from the previous state

**File and symbol:** `app/src/main/java/me/foxtails/palustris/ui/FeedViewModel.kt:154-175`, `FeedViewModel.loadMore`.

The method captures `state` and starts a request. The method does not capture a generation or verify the cursor after the request returns.

`refresh()` cancels `feedJob`, clears the feed, and starts a new request. Kotlin cancellation cannot stop a source that ignores cancellation after its network response arrives.

The old `loadMore` job then writes `state.posts + newPosts` into the current state. It can append old rows to the refreshed timeline and restore the old cursor. It can also replace optimistic interaction changes made while paging was active.

This can show stale posts, duplicate pages, or a wrong next page. The impact affects Home and any caller that reuses this ViewModel for a timeline.

**Confidence:** High from source inspection.

**Existing coverage:** `FeedViewModelReactionTest` covers action behavior. No test covers a delayed paging response after refresh.

**Missing proof:** Use a source fake that returns a suspended first page after cancellation. Start `loadMore`, call `refresh`, then release the old response. Assert that only the refreshed page and cursor remain.

### Medium: Direct-message responses ignore the current conversation

**File and symbol:** `app/src/main/java/me/foxtails/palustris/ui/directmessages/DirectMessageViewModel.kt:73-121,148-188`.

`loadMore`, `openConversation`, and `send` capture state before launching asynchronous work. Their completion paths update `_state` without checking the current conversation or request generation.

For example, a thread request for conversation A can finish after the user opens conversation B. The completion path then writes A's thread into the selected state for B. A send started in A can also select A again after the user navigates to B.

The same problem affects inbox paging. A refresh does not cancel the separate `loadMore` coroutine, and that coroutine can replace fresh conversations with its old merge.

This can display private messages in the wrong conversation and can move navigation back to an old conversation after a send.

**Confidence:** High from source inspection.

**Existing coverage:** `DirectMessageSourceTest` covers adapter requests. `DirectMessageViewModel` has no direct test coverage.

**Missing proof:** Delay thread, paging, and send fakes. Change the selected conversation before each response. Assert that stale responses do not change the selected conversation, thread, or loading state.

### Medium: Mastodon reaction probing uses an invalid capability test

**File and symbol:** `app/src/main/java/me/foxtails/palustris/data/mastodon/MastodonCapabilityProbe.kt:47-56,195-208`.

When instance metadata lists `pleroma_emoji_reactions`, the probe requests reactions for hardcoded status ID `1`.

The code maps every `ApiFailure` to `Ambiguous`. `parseCapabilities` then maps `Ambiguous` to `CapabilityStatus.Unsupported`.

A server can support the endpoint while status `1` does not exist, is private, or is inaccessible to the authenticated account. The probe then hides reaction mutation for a supported server.

The current test fixture returns a successful response for status `1`, so it verifies the sentinel assumption instead of the endpoint capability.

**Confidence:** High from source inspection and the existing fixture.

**Missing proof:** Test a verified extension whose sentinel request returns 404, 403, 429, and 500. Define an endpoint probe that does not depend on an arbitrary status, or keep mutation capability unknown until a real post mutation succeeds.

## New structural findings

### Medium risk: Application-lifetime maps retain server and media identities

The following maps grow for the lifetime of their owner and have no eviction policy:

- `EmojiAssetStore.urlLocks` at `data/emoji/EmojiAssetStore.kt:37` keeps one lock for every canonical URL.
- `MastodonDirectMessageService.directLastPosts` at `data/mastodon/MastodonDirectMessageService.kt:29` keeps one full post for every visited conversation or sent status.
- `MisskeySource.continuationStore` at `data/misskey/MisskeySource.kt:94,163-168` keeps abandoned thread acquisitions until the source is destroyed.
- `HttpClientPool.clients` at `data/misskey/HttpClientPool.kt:16-25` keeps a client for every visited connection and has no removal operation.

These owners have different purposes, so one global cache abstraction would not improve the boundary. Each owner needs a retention policy that matches its data.

This is a confirmed unbounded-retention design, but its memory impact needs measurement before assigning a higher severity.

**Confidence:** High for retention. Medium for user-visible memory impact.

**Existing coverage:** Emoji tests cover deduplication and download behavior. Direct-message source tests cover request mapping. Thread tests cover continuation identity. None measures repeated unique identities or abandoned sessions.

**Missing proof:** Run a synthetic repeated-server, repeated-URL, repeated-conversation, and abandoned-thread test. Measure retained map entries and heap size after garbage collection.

## Concurrency and lifecycle findings

The new feed and direct-message findings are lifecycle defects caused by cancellation without a publication guard.

`PhotoGridController`, `SearchController`, and `ProfileTimelinePager` already use generation or target checks. `FeedViewModel` and `DirectMessageViewModel` should use equivalent request ownership.

`UnifiedPushRegistrationManager.disable` catches broad exceptions at `:202-210`. That catch also catches coroutine cancellation. Sign-out cleanup can therefore continue after its owner is cancelled. The code intentionally makes server cleanup best effort, but it should preserve cancellation while isolating the remote cleanup operation.

## Persistence and compatibility findings

`RoomNotificationStore.read` at `data/notifications/NotificationStore.kt:57-63` decodes a stored JSON blob without the file store's `runCatching` fallback. A malformed Room row can fail notification observation and prevent normal recovery.

`NotificationRepository` still rewrites a complete account JSON blob for each persistent mutation. Delivery records and dismissal tombstones are not bounded by the visible 500-item limit. This remains an investigation item until storage latency and retention are measured.

The direct-message and emoji databases use version `1` with `exportSchema = false`. Future stored-format changes will not have generated schema history. The current code has no migration defect because no migration is present, but the missing schema artifact increases upgrade risk.

## Protocol boundary findings

The Mastodon reaction probe is the main new protocol defect. It converts a resource-specific response into a server capability decision.

`MisskeySource.create` validates reply origin at `:350`, but `MisskeySource.post` at `:102-105` does not validate the requested entity origin before sending an authenticated request. Callers that pass a foreign `EntityId` can therefore reach the Misskey API with that ID. The adapter should reject foreign IDs at the public method boundary.

`MastodonDirectMessageService` correctly validates conversation pagination origins, but its conversation cache is keyed only by the conversation value. The service is source-scoped, so account isolation holds while the source lives. The cache still requires an eviction policy.

## UI state and Compose findings

Home filtering and paging use different row collections. The visible list derives `visibleRows` after hashtag filtering, while the feed state retains all posts. This keeps the known R11 automatic paging defect active.

Settings subpage state remains `remember` rather than `rememberSaveable` in `ConnectedApp.kt:112-114`. Activity recreation can reopen the main settings page instead of the selected subpage.

The direct-message UI has adapter and screen coverage but no ViewModel state-transition coverage. The missing owner tests are more important than additional visual tests for this feature.

## Test blind spots

- No Feed test releases a cancelled, delayed paging response after refresh.
- No DirectMessageViewModel test changes selection during thread, paging, or send work.
- Mastodon probe tests assume status `1` exists when the extension probe succeeds.
- No test checks capability results for a missing, private, or foreign sentinel status.
- No test measures `urlLocks`, direct-message cache entries, HTTP clients, or thread continuations after repeated use.
- No notification persistence test corrupts the Room JSON row and observes recovery.
- No test verifies that `MisskeySource.post` rejects a foreign entity before network access.
- No test checks settings subpage restoration after activity recreation.
- Existing Compose tests do not prove physical compact, wide, font-scale, or Android 15 rendering behavior.
- Live-server protocol behavior remains unverified for supported Mastodon forks and Misskey-family servers.

## Recommended refactor order

1. Add deterministic stale-response tests for Feed and direct messages.
2. Add request generation and current-target checks to those owners.
3. Fix notification checkpoint query validation and the moderation removal marker cleanup.
4. Fix thread reaction overlay application and Saved Posts action-family ownership.
5. Replace the Mastodon sentinel probe with a capability-safe protocol check.
6. Add foreign-origin validation to `MisskeySource.post`.
7. Define retention policies for each application-lifetime map.
8. Define Room corruption recovery and schema migration policy.

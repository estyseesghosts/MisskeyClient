# Beeline Documentation Foundation

## 1. Current documentation state

The checkout contains useful documentation, but it does not yet have clear audience boundaries.
Several documents mix current facts, proposed work, historical evidence, and temporary task instructions.

### Current authorities

Use the following sources for the stated facts:

| Fact | Authority | Current evidence |
| --- | --- | --- |
| Runtime behavior | Application source | `app/src/main/java/me/foxtails/palustris/` |
| Intended behavior | Tests | `app/src/test/` and `app/src/androidTest/` |
| Build configuration | Gradle files | `build.gradle.kts`, `app/build.gradle.kts`, `gradle/libs.versions.toml` |
| CI verification | Workflow files | `.github/workflows/android.yml` and `.github/workflows/release.yml` |
| Repository rules | `AGENTS.md` | Naming, architecture, security, logging, and completion rules |
| Documentation style | `importantdocs/writing_style.md` | Short, active, consistent technical English |
| Historical verification | `logs/DONE.txt` and `logs/BUGS.txt` | Completed checks and unresolved limits |

Documentation must not override these authorities.

### Existing documents

- `README.md` is the public project introduction. It uses an informal style and contains old status claims.
- `AGENTS.md` is the current operational guide for agents and contributors. It contains more than an agent wiki needs.
- `docs/decomposition.md` is the strongest current engineering map. It records corrected ownership and repair risks.
- `docs/decomp/` contains earlier exploration briefs and reports. These reports remain useful evidence maps, not permanent ownership contracts.
- `docs/decomposition_2/` contains task briefs and completed exploration results. Each result has a narrow scope and should remain evidence for that task.
- `docs/roadmaps/notifications.md` is an implementation plan. `notifications_progress.md` reports later implementation progress. Their status language must remain separate.
- `docs/roadmaps/profile_timeline_roadmap.md` contains both an old implementation plan and a current implementation-status section. It also references the missing `profile_ui_roadmap.md`.
- `docs/LetsPolish.md`, `docs/interactionparity.md`, `docs/FIXTHISSHIT2.md`, and `docs/0.2.2.cont.md` are task specifications or visual plans. They are not permanent architecture documentation.
- `logs/` records work history and unresolved verification limits. It must not become the source for architecture rules.
- `.github/workflows/android.yml` runs unit tests, lint, debug assembly, release assembly, and an API 29 instrumentation job.
- `.github/workflows/release.yml` validates release tags, runs checks, builds a signed APK, verifies its signature, and publishes a release.

### Problems to address

- The README calls the application an unfinished prototype while current source and logs describe implemented direct messages, notifications, Photo Grid, profile timelines, and other features.
- The README says native Misskey chats are not implemented, but current direct-message behavior is a separate protocol-neutral feature. The product documentation must describe the supported direct-message behavior accurately.
- The README lists planned or untested integrations without a dated support matrix.
- Roadmaps contain proposed file names and future architecture beside implemented-status claims.
- Several documents repeat ownership rules. They can drift when code changes.
- The root `docs/` directory and `AGENTS.md` are ignored by the current Git rules. A repository-owned documentation plan therefore needs an explicit tracking decision.
- Product identity migration remains visible in source evidence. New documentation must use Beeline and must describe internal `Palustris` identifiers only when a compatibility explanation requires them.

The first documentation version should classify existing material before it adds new pages.

## 2. Documentation audiences

### Human contributors

Human contributors need a short project overview, reliable setup instructions, architecture orientation, feature ownership, build commands, and release checks.
They should not need to read task history or every source file before making a small change.

### Human users

Users need supported server families, feature limits, privacy statements, account behavior, and troubleshooting guidance.
User documentation must not expose internal package names or unfinished implementation plans.

### Agents

Agents need an engineering map.
The map must identify owners, boundaries, invariants, persistence contracts, protocol differences, affected tests, and verification limits.
It must prevent an agent from treating an old plan or a stale report as current source truth.

### Maintainers and reviewers

Maintainers need status evidence, release gates, open risks, and a simple rule for deciding whether a code change needs documentation.
Reviewers need to distinguish source-backed behavior from mocked, device, and live-server evidence.

### Code readers

Code readers need comments near non-obvious decisions.
They do not need a second copy of the function implementation in a wiki.

## 3. Source-of-truth policy

Use one authority for each kind of fact.

1. Application source defines implemented runtime behavior.
2. Tests define verified behavior and regression expectations.
3. Domain contracts define shared protocol-neutral behavior.
4. Protocol adapters define request shapes, mapping, pagination, and protocol-specific failures.
5. Gradle files define local build inputs and task configuration.
6. CI workflows define hosted verification and release automation.
7. `AGENTS.md` defines repository operation and non-negotiable constraints.
8. Logs define historical work and verification limits.
9. Human documentation explains stable behavior for users and contributors.
10. Agent documentation explains ownership and invariants without replacing source or tests.

Keep maintained documentation in the main repository when possible.
Publish human pages from that source or synchronize them through a reviewed process.
Do not maintain a second independently edited copy of architecture text in a wiki.

The recommended layout is:

- `README.md` for the short public entry point;
- `docs/wiki/` for human-facing maintained pages;
- `docs/agent/` for agent-facing engineering pages;
- `docs/reference/` for generated or protocol reference material;
- `docs/archive/` for completed plans that still provide historical value;
- `logs/` for chronological task evidence only.

The current ignored status of `docs/` requires a maintainer decision before this layout becomes a tracked source.
Do not force-add files or change ignore rules as part of this exploration.

Every maintained page should include:

- an owner or owning subsystem;
- a last-reviewed date;
- links to authoritative code and tests;
- a status such as `current`, `planned`, `historical`, or `reference`;
- explicit unverified claims when runtime or live-server evidence is missing.

When a page conflicts with source, update or remove the page.
Do not preserve a conflicting page because it has historical names or detailed prose.

## 4. Human wiki structure

Keep the first human wiki small.
The following pages provide useful coverage without reproducing the agent map.

### `Overview`

Purpose: explain what Beeline is and which server families it supports.

Include the Android support range, supported Mastodon-compatible and Misskey-family behavior, current feature status, privacy limits for direct messages, and known live-validation limits.
Link to troubleshooting and release information.

### `Architecture`

Purpose: give contributors a high-level map of the single Android module.

Include the `domain`, `data`, protocol adapter, authentication, persistence, notification, and `ui` boundaries.
Describe `SocialSource`, `SocialSourceFactory`, `AccountSourceRegistry`, and `AccountManager` without listing every class.
Link to the agent ownership map for implementation detail.

### `Accounts And Sessions`

Purpose: explain account isolation and authentication behavior.

Include validated HTTPS origins, protocol and local identity binding, session replacement, account switching, sign-out, encrypted secrets, and account-scoped cleanup.
State that tokens and push keys do not belong in logs or ordinary documentation.

### `Server Compatibility`

Purpose: explain supported protocol behavior and version limits.

Include a dated matrix for Mastodon-compatible and Misskey-family servers, capability states, supported endpoints, pagination differences, direct messages, notifications, and known unverified cases.
Keep server-specific request details in the agent wiki or reference pages.

### `Data And Privacy`

Purpose: explain local storage, migrations, retention, and sensitive data handling.

Include account-scoped preferences, drafts, notification data, media and emoji caches, no-backup storage, encryption boundaries, Room schema ownership, and removal behavior.
Link to migration notes when a stored format changes.

### `UI And Navigation`

Purpose: help contributors understand the visible application structure.

Include compact and wide layouts, navigation destinations, Photo Grid independence, profile and thread behavior, Compose state restoration, accessibility expectations, and system font considerations.
Keep detailed state ownership in the agent wiki.

### `Notifications And Direct Messages`

Purpose: explain the user-visible behavior of notification delivery and direct messages.

Include inbox filters, unread precision, local seen state, server acknowledgement, Android presentation, push limitations, account routing, direct-message privacy limits, and offline behavior.
Do not claim that direct messages are encrypted or secure.

### `Build Test And Release`

Purpose: provide commands and expected verification for contributors.

Include Java and Android SDK requirements from Gradle and CI, unit tests, lint, debug and release assembly, API 29 instrumentation, release tag format, signing requirements, and artifact locations.
Link to workflow files instead of copying the complete YAML.

### `Troubleshooting And Contribution`

Purpose: explain common local failures and the contribution process.

Include missing SDK or signing inputs, locked-device Compose failures, live-server limitations, secret-handling rules, focused test selection, documentation review, and the definition of done.
Keep unresolved findings in `logs/BUGS.txt` until maintainers resolve them.

## 5. Agent wiki structure

The agent wiki is an engineering map.
It must answer where behavior belongs and which contracts a change must preserve.

### `Start Here`

Purpose: give an agent the reading order and authority rules.

Include the source hierarchy, product naming rules, package boundary, current module shape, status labels, required verification, and a warning that plans are not proof of implementation.

### `Ownership Map`

Purpose: identify the owner of each major behavior.

Include the following current boundaries:

| Area | Primary owner | Do not move into |
| --- | --- | --- |
| Accounts and sessions | `AccountManager` | Compose screens or protocol mappers |
| Source construction | `AccountSourceRegistry` and `SocialSourceFactory` | Individual screens |
| Shared contracts | `domain/` and `SocialSource` | Protocol JSON classes |
| Misskey transport and mapping | `data/misskey/` | Shared domain or generic UI |
| Mastodon transport and mapping | `data/mastodon/` | Shared domain or generic UI |
| Notification merge and durable state | `NotificationRepository` | ViewModels or push presentation |
| Notification presentation policy | `NotificationDeliveryPlanner` | Repository synchronization |
| Preferences | Preference repositories | Compose-local mutable state |
| Direct messages | `data/directmessages/` and its ViewModel/UI owners | Notification identity or native Misskey Chat assumptions |
| Media | `data/media/` and media UI owners | Protocol mappers unless mapping metadata requires it |
| Compose shell and navigation | `PalustrisApp` and focused shell state | Data repositories |
| Feature presentation state | Feature ViewModels and feature UI packages | One global app ViewModel |

### `Where To Change X`

Purpose: provide a task-oriented lookup table.

Include entries for:

- account add, reauthentication, switching, and removal;
- source selection and capabilities;
- Misskey or Mastodon request and mapping behavior;
- feed, search, Photo Grid, profile, thread, and saved collections;
- direct messages;
- notification ingestion, persistence, push, and Android presentation;
- drafts and post preferences;
- media decoding and cache behavior;
- localization and display settings;
- navigation and saved-state restoration;
- build, lint, release, and instrumentation changes.

Each entry should name the owner, the relevant contract, and the first tests to read.

### `Cross-Cutting Invariants`

Purpose: record rules that apply across features.

Include multi-account isolation, session generation and revision checks, opaque cursors, validated origins, token secrecy, cancellation after suspension, normalized errors, unknown capability states, nullable interaction counts, account-scoped persistence, and no initial notification alert storm.

### `Protocol Boundaries`

Purpose: record differences that generic code must not absorb.

Include Misskey and Mastodon endpoint shapes, mapping rules, pagination ownership, capability probing, direct-message semantics, notification read behavior, and unsupported versus denied versus temporary failure states.
Link to adapter contracts and fixtures.

### `Persistence Contracts`

Purpose: record formats that require backward compatibility.

Include session storage, notification JSON version `2`, Room migrations, drafts, preferences, emoji cache formats, account removal, legacy import behavior, enum fallbacks, and opaque identifiers.
Each entry must identify its migration or compatibility test.

### `UI State And Lifecycle`

Purpose: record Compose ownership and lifecycle rules.

Include shell navigation state, feature ViewModel lifetimes, account and session keys, `rememberSaveable` boundaries, compact and wide layouts, IME behavior, floating-control clearance, and foreground stream ownership.

### `Verification Map`

Purpose: connect change types to tests and evidence limits.

Include focused JVM tests, Compose tests, adapter contract tests, persistence tests, lint, build, instrumentation, device checks, and live-server checks.
State what each layer cannot prove.

### `Documentation Workflow`

Purpose: tell an agent how to update documentation during a code change.

Include status labels, link review, affected-page review, log rules, source and test references, and the final documentation checklist.

Do not copy full source algorithms into these pages.
Use named symbols and links to the code and tests.

## 6. Code comment and KDoc policy

Add a comment when the reason is not clear from the code.
Use comments for the following cases:

- compatibility with an older stored format or server version;
- account, session, generation, or lifecycle invariants;
- concurrency rules and cancellation requirements;
- security or origin validation boundaries;
- protocol quirks and intentionally different adapter behavior;
- non-obvious fallback or partial-data behavior;
- bounds that protect memory, storage, network, or rendering cost;
- performance choices that reject a simpler but unsafe implementation.

Use KDoc when a public or package-level contract is not clear from its type signature.
Document input ownership, output guarantees, error meaning, cursor opacity, and lifecycle requirements when applicable.

Do not comment obvious assignments, simple delegation, or visible Kotlin syntax.
Do not use a comment to preserve an obsolete plan.
Update or remove a comment when source behavior changes.
Keep comments near the code that enforces the rule.

For a complex invariant, prefer this structure:

1. State the rule.
2. State the failure prevented.
3. Name the compatibility or lifecycle reason when needed.

Comments must use Beeline as the product name.
Use `Palustris` only for an existing internal identifier or a compatibility explanation.

## 7. Documentation maintenance rules

Documentation is part of the definition of done when a change affects a documented fact.
Update the documentation in the same implementation slice when a change affects:

- user-visible behavior or feature availability;
- ownership or module boundaries;
- persistence, migrations, retention, or privacy;
- protocol support, endpoint behavior, mapping, or capabilities;
- build, release, signing, or CI steps;
- required tests or verification evidence;
- a security, lifecycle, concurrency, or compatibility invariant.

Do not edit documentation for a private implementation change that leaves all documented behavior unchanged.

Use this review checklist:

- Read the current source and affected tests.
- Identify the owner before changing the owner map.
- Check account and session isolation.
- Check protocol boundaries and capability states.
- Check persistence and migration effects.
- Check compact, wide, font-scale, and accessibility effects for UI changes.
- Add or update comments for non-obvious invariants.
- Update the matching human or agent page.
- Remove stale claims from pages touched by the change.
- Link the page to current symbols and tests.
- Record device or live-server limits without overstating them.
- Update `logs/DONE.txt`, `logs/TODO.txt`, or `logs/BUGS.txt` when the task requires it.
- Run the relevant focused checks and the required project checks.

The reviewer should reject a documentation update that only copies source text.
The update must explain ownership, user impact, or maintenance action.

## 8. Refactor integration

Document stable boundaries as each refactor slice is finalized.
Do not publish a complete ownership model immediately before replacing that model.

Use this sequence during the remaining refactor:

1. Record the current owner, callers, invariants, and tests before a risky move.
2. Mark the record as a refactor note, not as final architecture.
3. Add characterization tests for behavior that the move must preserve.
4. Implement one coherent structural or repair slice.
5. Update the agent ownership map when the new boundary is stable.
6. Update the human page only when the change affects contributor or user understanding.
7. Remove the temporary plan when it no longer adds evidence.
8. Record unresolved device, live-server, or policy questions in the appropriate log.

The current `docs/decomposition.md` should remain the active refactor guide until the refactor ends.
The future agent wiki should link to it instead of duplicating its full slice order.

Write invariants before or with risky changes to notifications, sessions, persistence, pagination, protocol mapping, and Compose state restoration.
Write verification notes with the implementation, not after an unsupported completion claim.

## 10. Verification and drift prevention

Use a layered verification process.

- Check every page for a status, review date, owner, and source links.
- Check that code paths named by a page still exist.
- Check that test names and Gradle commands still exist.
- Compare build instructions with `.github/workflows/android.yml` and `release.yml`.
- Search for old product names in new user-facing documentation.
- Search for stale feature claims such as `not implemented`, `placeholder`, or `untested` before publishing a status page.
- Review protocol claims against adapter tests and capability code.
- Review persistence claims against stores, migrations, codecs, and restart tests.
- Review account claims against `AccountManager`, session tests, and account-removal paths.
- Review UI claims against Compose tests and both compact and wide layout owners.

Add a lightweight documentation check to CI when the documentation source is tracked.
The check should validate Markdown links, required page metadata, forbidden user-facing codename use, and references to missing files.
It should not require a large documentation dependency for simple checks.

Run documentation review in every feature pull request.
Run a full source-to-documentation audit before each release.
Use the release workflow as the build and signing reference, not a copied command list.

Label evidence precisely:

- `source verified` means code inspection found the behavior.
- `test verified` means an automated test passed.
- `device verified` means a named device run passed.
- `live verified` means a real supported server or delivery path passed.
- `unverified` means the evidence is absent or incomplete.

Do not use a passing mock test as live-server evidence.
Do not use a Compose test as proof of every physical device layout.
Do not use a release assembly as proof of signed release publication unless the workflow verified the signature.

# External Link Ownership

## 1. Current ownership

`PostRow.kt` declares the package `me.foxtails.palustris.ui` even though its path is `ui/posts` (`PostRow.kt:7`).

`PostRow.kt:95-100` owns the current browser launch function, `openExternal`.

- It accepts a nullable URL.
- It prepares the URL through `ExternalLinkHandler.prepare`.
- It parses the prepared value as an Android `Uri`.
- It accepts only `http` and `https` URLs with a non-blank host.
- It creates an `Intent` with `Intent.ACTION_VIEW`.
- It catches `ActivityNotFoundException`.
- It shows `R.string.error_no_app_open_link` when no activity can open the URL.

`ExternalLinkHandler` already exists in the focused `ui.links` package (`ui/links/ExternalLinkHandler.kt:1-16`).

- `ExternalLinkHandler.cleanTrackingParameters` stores the application preference (`ExternalLinkHandler.kt:7-8`).
- `ExternalLinkHandler.prepare` delegates cleanup to `TrackingParameterCleaner` (`ExternalLinkHandler.kt:10`).
- `ExternalLinkHandler.open` currently prepares the URL and delegates browser launching back to `me.foxtails.palustris.ui.openExternal` (`ExternalLinkHandler.kt:12-15`).

The qualified call makes `ExternalLinkHandler` depend on a function declared in `PostRow.kt`.
The dependency exists even though `ExternalLinkHandler.kt` does not import `PostRow.kt`.

`TrackingParameterCleaner` owns the cleanup algorithm (`domain/TrackingParameterCleaner.kt:6-38`).
It removes known attribution parameters only when its `enabled` argument is true.
It preserves malformed, non-web, hostless, queryless, and signed URLs.

`ConnectedApp` assigns the preference to `ExternalLinkHandler.cleanTrackingParameters` (`ConnectedApp.kt:99-104`).
This is the current application-wide preference bridge.

## 2. Current callers

The current production code has eight invocations of `openExternal`.

- `PostRow.kt:273` opens a quoted post when the quote card is clicked.
- `InlineEmojiText.kt:94` opens a URL when no `onOpenUrl` callback exists for inline content.
- `InlineEmojiText.kt:152` opens an annotated URL when no `onOpenUrl` callback exists for a text tap.
- `NotificationDetailScreen.kt:89` opens a notification route URL with the `Open on server` button.
- `NotificationDetailScreen.kt:158` opens a cached post URL with the `Open on server` button.
- `ProfileDetails.kt:49` opens a profile field value when the value starts with `http://` or `https://`.
- `MediaViewerScreen.kt:376` opens the current attachment URL from the media viewer browser action.
- `SinglePostScreen.kt:293` opens a quoted post from the detailed post screen.

These callers use generic external navigation.
None of them needs post-specific browser behavior.

`PostRow.kt:226` and `PostRow.kt:238` pass `onOpenUrl` into `PostBodyText`.
`PostBodyText` passes it to `InlineEmojiText` (`PostRow.kt:338-360`).
When a caller supplies the callback, the callback owns that URL action.
When the callback is absent, `InlineEmojiText` uses the generic fallback above.

The current imports of `openExternal` occur in these files:

- `InlineEmojiText.kt:54`.
- `NotificationDetailScreen.kt:29`.
- `ProfileDetails.kt:23`.
- `ProfileScreen.kt:69`.
- `MediaViewerScreen.kt:72`.
- `SinglePostScreen.kt` has a same-package use through its `ui` package declaration.

`ProfileScreen.kt:69` is a stale import.
`ProfileScreen.kt` does not call `openExternal`; `ProfileDetails.kt` owns the actual profile-field call.

`ExternalLinkHandler.prepare` has three current production consumers outside its own implementation.

- `PostRow.kt:96` uses it before browser opening.
- `PostRow.kt:842` uses it before post sharing.
- `PostShareSheet.kt:421` uses it before copying a post link.

The post sharing and copy paths are generic URL preparation, but they are not browser launching.
They should continue to use the focused link owner after this refactor.

There is no current production caller of `ExternalLinkHandler.open`.
The method currently exists as an incomplete owner because it delegates back to `PostRow.kt`.

The current normal external-link `ACTION_VIEW` intent exists in `PostRow.kt:98`.
`ConnectedApp.kt:304-309` also starts an `ACTION_VIEW` intent, but that URL belongs to the authentication flow.
`AccountManager` owns the related `browserUrl`, `browserOpened`, and `browserFailed` state (`AccountManager.kt:46-55, 143-187`).
That authentication intent is feature-specific and must not move into the generic post-link owner.

`NotificationLaunchRouter.kt:137-143` creates an `ACTION_VIEW` intent for the internal `palustris://notification/open` notification route.
It is an application deep link, not a normal external browser link.
It must remain in the notification routing owner.

## 3. Correct owner

Use the existing `me.foxtails.palustris.ui.links.ExternalLinkHandler` as the generic external navigation owner.
Do not create another browser or link utility.

Keep `TrackingParameterCleaner` as the domain owner of parameter rules and URL rewriting.
Keep `ExternalLinkHandler.prepare` as the setting-aware preparation entry point.

Move the behavior currently in `openExternal` into `ExternalLinkHandler.open`.
The moved method should own the complete generic navigation sequence.

- Return without an action for a null URL.
- Return without an action for a blank URL.
- Prepare the URL once through `prepare`.
- Parse the prepared URL.
- Reject URLs without an `http` or `https` scheme.
- Reject URLs with a blank host.
- Create the `Intent.ACTION_VIEW` intent.
- Catch `ActivityNotFoundException`.
- Show the existing no-application message after that failure.

`PostRow.kt` should call `ExternalLinkHandler.open(context, quote.url)` at both quote-card sites.
The `PostRow.kt` browser function should then be removed.

The remaining generic callers should import `ExternalLinkHandler` from `ui.links` and call `open`.
This applies to `InlineEmojiText`, `NotificationDetailScreen`, `ProfileDetails`, `MediaViewerScreen`, and any detailed-post caller that directly opens a quote.

The historical design prepares a URL twice when `ExternalLinkHandler.open` is used.
`ExternalLinkHandler.open` calls `prepare` at line 14, then the current `openExternal` calls `prepare` again at `PostRow.kt:96`.
The refactor must make `ExternalLinkHandler.open` the only preparation point for browser opening.
Do not implement the move by calling the existing method without removing its delegation and duplicate preparation.

The `sharePost` preparation at `PostRow.kt:842` and the copy preparation at `PostShareSheet.kt:421` should remain single calls to `ExternalLinkHandler.prepare`.
The `cleanTrackingParameters` argument on `sharePost` is currently unused (`PostRow.kt:841`).
Do not change that unrelated API as part of this small browser-owner move.

## 4. Behavior that must stay unchanged

- Valid `http` and `https` URLs open through the matching system handler.
- Null URLs do nothing.
- Blank URLs do nothing after parsing and validation.
- URLs with no host do nothing.
- Non-HTTP schemes do nothing.
- The existing `ActivityNotFoundException` path remains safe.
- The existing `error_no_app_open_link` message remains the failure message.
- The tracking preference controls cleanup before external navigation.
- Disabled cleanup returns the original URL.
- Enabled cleanup removes only the known attribution parameters.
- Signed URLs remain unchanged.
- Other query values, raw paths, authorities, and fragments remain unchanged by cleanup.
- Post sharing continues to prepare the post URL before creating its share intent.
- Post link copying continues to prepare the post URL before writing the clipboard value.
- Supplied `onOpenUrl` callbacks continue to receive the original parsed target.
- Generic fallback opening remains available when no callback exists.
- Authentication browser state continues to clear on a successful launch attempt.
- Authentication failure continues to update `AccountManager` rather than show the generic link error.
- Notification deep-link intents continue to use the `palustris://notification` route.

The generic owner should not add deep-link routing, in-app browser behavior, origin policy, or new navigation state.

## 5. Import and dependency cleanup

Remove the `openExternal` declaration and its browser-only dependencies from `PostRow.kt`.
Keep `Context`, `Intent`, and `Toast` in `PostRow.kt` because `sharePost` still uses them.
Remove `androidx.core.net.toUri` from `PostRow.kt` if no other code in that file uses it.

Add the `ExternalLinkHandler` import to each caller that moves from `openExternal` to `ExternalLinkHandler.open`.
Remove the stale `me.foxtails.palustris.ui.openExternal` import from `ProfileScreen.kt`.

The resulting `ExternalLinkHandler.kt` must not import `PostRow.kt`, `me.foxtails.palustris.ui.posts`, or another feature-specific UI owner.
Its browser implementation may depend on Android link APIs, the existing resource, and `TrackingParameterCleaner`.

Search for these symbols after the change:

- `openExternal` must have no declaration or call.
- `ExternalLinkHandler.open` must own every generic browser call.
- `ExternalLinkHandler.prepare` must remain in the share and copy paths.
- `Intent.ACTION_VIEW` must remain only for generic links, authentication, and the internal notification route.

## 6. Refactor order

1. Move the `openExternal` implementation into `ExternalLinkHandler.open`.
2. Remove the second preparation step from the new implementation.
3. Preserve the existing URL validation and failure message.
4. Replace the two `PostRow.kt` quote-card calls with `ExternalLinkHandler.open`.
5. Replace the generic callers in `InlineEmojiText`, `NotificationDetailScreen`, `ProfileDetails`, `MediaViewerScreen`, and `SinglePostScreen`.
6. Remove the stale `openExternal` imports.
7. Leave authentication browser handling and notification routing unchanged.
8. Leave post sharing, link copying, and composer text cleanup unchanged.
9. Search for stale declarations, calls, and imports.

This order keeps the generic owner valid before callers change.
It also limits the slice to browser ownership and import cleanup.

They cover removal of known attribution parameters, preservation of other query values, signed URLs, and composer text cleanup.

Existing UI tests cover link parsing and callback routing, but they do not test generic browser launching.

- `InlineEmojiTextTest.kt:164-182` checks that a URL action does not invoke the ordinary text fallback.
- `PostShareSheetTest.kt:34-66` covers the share sheet actions, but it does not verify the prepared clipboard value.

Add the smallest focused external-handler test set in `ui.links`.

- Verify that a valid URL starts one `ACTION_VIEW` intent with cleanup enabled.
- Verify that cleanup disabled preserves the URL query.
- Verify that null, blank, invalid-scheme, and hostless values do not start an activity.
- Verify that `ActivityNotFoundException` does not escape the handler.

Use the existing Robolectric test setup because `ExternalLinkHandler.open` needs an Android `Context` and an Android `Intent`.
Use a test context or a small fake context to capture `startActivity` without starting a real browser.

Keep `TrackingParameterCleanerTest` as the unit coverage for parameter rules.
Do not duplicate all cleaner cases in the browser-owner test.

After implementation, run symbol and import searches for `openExternal`, `ExternalLinkHandler`, and `ACTION_VIEW`.
Run the focused tracking, inline-text, and share-sheet tests.
Run the required Windows checks:

- `gradlew.bat test`
- `gradlew.bat assembleRelease`

The tests cannot prove behavior with every installed browser or every live server.

## 8. Risks and open questions

- `ExternalLinkHandler.cleanTrackingParameters` is mutable global state updated during `ConnectedApp` composition.
  The requested move should preserve this mechanism, but a later task may need a clearer preference owner.
- `sharePost` accepts `cleanTrackingParameters` but ignores the argument.
  Its current caller relies on the global handler setting, so changing this behavior would exceed this refactor.
- `ExternalLinkHandler.open` currently has no production caller.
  The implementation must receive focused tests before callers move to it.
- Only `ActivityNotFoundException` is caught today.
  The refactor should preserve that behavior unless a separate failure-policy decision requires handling other exceptions.
- The profile-field click test surface is small.
  The existing `isWebAddress` check and the handler host validation should remain separate.
- The caller callback contract passes original URL targets.
  Cleanup belongs to the generic action, not to the rich-text parser or post model.
- Authentication and notification `ACTION_VIEW` intents look similar to browser intents.
  A broad search-and-replace could break account login or notification routing.
- The source package and file path for `PostRow.kt` differ.
  Import cleanup must follow the package declaration, not the filesystem path.

# Notification Codec Boundary Review

## Current codec ownership

The boundary is incomplete.

`NotificationJsonCodec.kt:6-43` owns only the state-level `encode` and `decode` entry points. The entry points are used by both stores in `NotificationStore.kt:31-46` and `NotificationStore.kt:52-66`. The Room store stores the JSON blob in `notification_state.stateJson`. The legacy file store reads and writes the same JSON format. `LegacyNotificationFileImporter` therefore also depends on this contract.

The recursive codec implementation remains in `NotificationRepository.kt:525-1094`. It includes push registration, settings, delivery records, notifications, posts, accounts, activities, destinations, targets, groups, unread state, and checkpoints. The helpers are `internal` only because the entry points were moved to another file. No current caller outside this package requires that visibility. After the move, the recursive helpers should be private to `NotificationJsonCodec.kt`; only the state entry points should remain package-visible for the stores.

The following declarations are not JSON codec logic:

- `AccountId.stableFileName()` at `NotificationRepository.kt:520-523` hashes the account identity for storage filenames and Room keys. It belongs with notification store support, not in the JSON codec.
- `Notification.matches` at `NotificationRepository.kt:1098-1101` filters repository snapshots by a query. It belongs to repository behavior.
- `stableNotificationId` at `NotificationRepository.kt:1115` creates an Android delivery ID and is used by `NotificationPageMerge.kt:79`. It belongs with delivery identity or page merging, not in the codec.

The repository class itself, `NotificationRepository.kt:56-518`, owns state-flow loading, generation validation, atomic state transitions, page merging calls, delivery claims, account removal, and current-token persistence. Those responsibilities must remain there. The codec must not read repository maps, publish flows, validate sync tokens, call `NotificationStore`, or perform protocol requests.

## Code that belongs in NotificationJsonCodec

Move the following declarations without changing their bodies, keys, defaults, visibility semantics, or exception behavior. They are pure conversion between domain values and `JSONObject` values.

- State serialization at `NotificationJsonCodec.kt:6-43` remains the public package-local boundary. Keep top-level keys, version `2`, array filtering, optional fields, and state defaults unchanged.
- `encodePushRegistration` and `decodePushRegistration` at `NotificationRepository.kt:525-581` own the complete persisted push registration contract. They write account identity, generation, session revision, distributor and server endpoints, remote ID, endpoint generations, registration state, retry fields, errors, failure stage and reason, and retry time. Keep the connected-state fallback from the old single `endpoint` field to `serverEndpoint`.
- `encodeSettings` and `decodeSettings` at `NotificationRepository.kt:583-610` own notification preference JSON. Keep the `categories` set behavior, the empty-category distinction, quiet-hour omission, and default settings behavior.
- `encodeDelivery` and `decodeDelivery` at `NotificationRepository.kt:612-637` own the durable delivery record. Keep claim ID, claim expiry, retry count, attempt time, error category, Android tag, and Android ID. Do not move claim creation or claim validation here.
- `encodeNotification` and `decodeNotification` at `NotificationRepository.kt:639-679` own the notification persistence graph. They serialize identity, receiving account, creation time, typed activity, actors, target, destination, post, five read-state fields, raw type, and group.
- `encodeDestination`, `decodeDestination`, `encodeTarget`, and `decodeTarget` at `NotificationRepository.kt:681-693` and `NotificationRepository.kt:941-955` own the typed navigation representation. Preserve `in_app`, `server`, `post`, `profile`, `poll`, and `conversation` values. Preserve the fallback that creates an in-app destination from a legacy top-level `target` when `destination` is absent.
- `encodeEntity`, `decodeEntity`, `encodeAccountId`, and `decodeAccountId` at `NotificationRepository.kt:695-705` own persisted identity shapes. Keep connection strings, origin, protocol enum names, and local IDs exact. Do not add origin validation during this move; current store reads do not validate that the decoded state belongs to the filename account.
- `encodeAccount`, `decodeAccount`, `encodeEmoji`, `decodeEmoji`, `encodeEmojiMap`, and `decodeEmojiMap` at `NotificationRepository.kt:707-782` own the nested account and custom-emoji graph. Preserve profile fields, nullable URLs, nullable counts, moved-account recursion, aliases, visibility, submission values, and HTTPS URL validation.
- `encodePost` and `decodePost` at `NotificationRepository.kt:784-872` own the nested post graph. Preserve recursive quotes, attachments, reactions, available actions, nullable interaction counts, poll options, custom emoji, selected reactions, wrapper/action IDs, and existing defaults.
- `encodeAttachment`, `decodeAttachment`, `encodeReaction`, `decodeReaction`, `encodeEmojiChoice`, and `decodeEmojiChoice` at `NotificationRepository.kt:874-933` are post sub-codecs and should move with the post codec. Keep MIME-derived media-kind fallback, nullable media dimensions, non-negative interaction count handling, and reaction count clamping.
- `encodeActivity` and `decodeActivity` at `NotificationRepository.kt:957-1030` own the activity discriminant. Preserve every current kind string, system-kind fallback, unknown fallback text, legacy reaction `imageUrl` support, and validated server destination handling.
- `encodeGroup` and `decodeGroup` at `NotificationRepository.kt:1032-1043` own grouped notification JSON. Preserve group account identity, group value, actor previews, and the current positive-count behavior.
- `encodeUnread` and `decodeUnread` at `NotificationRepository.kt:1045-1061` own exact, at-least, present, none, and unknown unread states. Preserve non-negative count normalization and unknown fallback.
- `encodeCheckpoint` and `decodeCheckpoint` at `NotificationRepository.kt:1063-1094` own query and cursor persistence. Preserve category names, sorted query key generation outside the codec, limits, grouping, opaque cursor values, completeness enum fallback, baseline state, and captured time.
- `optLongOrNull`, `optIntOrNull`, and `optionalNonNegativeInt` at `NotificationRepository.kt:935-939` and `NotificationRepository.kt:1103-1113` are JSON decoding helpers. Move them with the codec. Do not replace them with generic coercion because their null, malformed, and negative-value behavior is part of the current contract.

The nested account and post helpers are still codec logic even though their models are shared domain models. They do not parse Misskey or Mastodon payloads. Protocol mappers must continue to produce domain models before the persistence codec sees them.

## Code that must stay in NotificationRepository

Keep the `NotificationRepository` class and its synchronization boundary unchanged. In particular, the following behavior must not move into `NotificationJsonCodec.kt`:

- Lazy state loading and `MutableStateFlow` creation.
- Generation activation, invalidation, token recovery, and current-token checks.
- Account and connection-origin checks for incoming pages and stream events.
- Page merge orchestration and publication of the next immutable state.
- Read-state, dismissal, settings, and push-registration mutations.
- Delivery claim creation, UUID generation, lease assignment, stale-claim rejection, and completion.
- The final generation check before persistence.
- Account removal and store deletion ordering.
- Snapshot filtering through `Notification.matches`.

`NotificationStore` must remain the storage owner. `FileNotificationStore`, `RoomNotificationStore`, and `LegacyNotificationFileImporter` should call only the state-level codec boundary. They must not call recursive helpers directly or duplicate JSON parsing.

`AccountId.stableFileName()` should be moved to `NotificationStore.kt` or another focused storage-identity owner in a separate small cleanup. `stableNotificationId` should be moved to `NotificationPageMerge.kt` or a focused delivery-identity owner in a separate cleanup. Neither helper belongs in `NotificationJsonCodec.kt`. These moves should not be combined with a persistence format change.

Do not move `NotificationPageMerge`, `NotificationReadStateMerge`, or `NotificationDeliveryTransforms` into the codec. They transform repository state and delivery behavior rather than JSON values.

## Serialization contract

The installed format is a version-2 account-scoped JSON object. The encoder writes:

| JSON field | Current behavior |
| --- | --- |
| `version` | Always writes numeric `2`. The decoder currently ignores this value. |
| `items` | Writes notification objects. Invalid array entries are skipped during decode. Missing or invalid arrays decode to an empty list. |
| `unread` | Always writes a typed unread object. Missing or unknown values decode to `Unknown`. |
| `checkpoint` | Written only when the compatibility checkpoint is non-null. A malformed singular checkpoint can fail the complete decode. |
| `lastSyncedAt` | Writes the epoch-millisecond value. Missing values decode to `0`. |
| `dismissedIds` | Writes entity objects. Invalid entries are skipped and the result is a set. |
| `checkpoints` | Writes an object keyed by the stable query fingerprint. Invalid individual entries are skipped. |
| `deliveries` | Writes delivery records. Invalid individual entries are skipped, then records are indexed by notification ID. A later duplicate ID wins according to the current JSON iteration behavior. |
| `settings` | Always writes settings. Missing settings decode to `NotificationSettings()`. |
| `pushRegistration` | Written only when non-null. A malformed value can fail the complete decode. |

Each notification writes `id`, `accountId`, `createdAt`, `activity`, `actors`, `readStatus`, the four local/presentation and acknowledgement flags, and `rawType`. `target`, `destination`, `post`, and `group` are optional. A target without a destination is intentionally reconstructed as an in-app destination for legacy compatibility.

Activity compatibility includes these exact discriminants: `mention`, `reply`, `reshare`, `quote`, `favourite`, `reaction`, `follow`, `follow_request`, `accepted_request`, `subscribed`, `poll_result`, `post_update`, `quoted_post_update`, `direct_message`, `system`, and `unknown`. Unknown system kinds become `System.AppEvent`. Unknown activity kinds remain `NotificationActivity.Unknown` with fallback text and an optional validated HTTPS server destination. Legacy reaction `imageUrl` is converted to a validated custom emoji when possible.

The post graph writes the current fields for identity, author, text, time, audience, attachments, warning, reshare author, reply IDs, reactions, action names, URL, nullable interaction counts, recursive quote, polls, booleans, selected reaction choices, emoji, own repost ID, and action target ID. The current codec does not write `Post.contentVisibility`; decoding therefore defaults it to `Visible`. This omission is an existing behavior and must not be silently changed by the extraction.

The group codec writes account identity, group value, actor previews, and `totalCount`. It does not write `NotificationGroup.actorContinuation`; decoding defaults that field to null. This is also an existing omission.

Enum handling is intentionally tolerant in several places. Unknown activity kinds, system kinds, read statuses, delivery states, push states, failure stages, failure reasons, media kinds, post audiences, post actions, notification categories, completeness values, and legacy reaction fields use the current fallback or skip behavior. Do not replace `valueOf` and `runCatching` combinations with a new common enum policy.

All cursors are opaque strings. The codec must not parse, sort, compare, or reconstruct them. Time values are stored as numeric epoch milliseconds. Entity and account identifiers are stored as strings and must not be interpreted as numeric IDs.

## Compatibility hazards

- Version `2` is the active installed format. Old Beeline versions can have written both the pre-Room atomic file and Room `stateJson` with this shape. The importer reads the atomic file through `FileNotificationStore`, then writes the decoded state back through the same codec. Do not add a new version or rewrite old keys during this extraction.
- The legacy file path catches all read and decode failures and returns no state. The Room path does not catch exceptions from a malformed stored JSON blob. Preserve this difference during the move. Choosing a new corruption-recovery policy is a separate storage repair.
- A malformed top-level checkpoint, push registration, account identity, target, or settings value can discard the complete store read, while many malformed array entries are dropped individually. This uneven behavior is observable and needs fixed tests before any hardening change.
- `NotificationRepositoryState.checkpoints` uses the exact `NotificationQuery.stableKey` as an object key. Do not rename, normalize, or rebuild the key in the codec.
- JSON object key order is not a contract. Tests must compare fields and decoded values, not the string order produced by `JSONObject`.
- URL validation is part of the persisted safety boundary. Invalid, non-HTTPS, credential-bearing, or fragment-bearing server destinations and custom-emoji URLs are dropped according to the existing domain validators.
- The codec does not enforce account ownership against the `NotificationStore` account argument. Adding such a check could change recovery behavior for files containing mismatched state. Treat account isolation as a separate explicit test and decision.
- Widening all helpers to `internal` created unnecessary package coupling in the previous partial move. Narrowing recursive helpers back to private scope is safe because current callers are in the codec itself.
- Do not import protocol JSON types or protocol mapper code into the codec. The codec must remain below the shared domain boundary and independent of network payload shapes.

## Known notification issues found during review

1. The v0.2.1 unknown-activity server-destination defect is fixed in the current source. `encodeActivity` writes the validated server URL at `NotificationRepository.kt:983-985`, and `decodeActivity` restores it at `NotificationRepository.kt:1023-1029`. `NotificationRepositoryTest.unknownActivityPreservesValidatedNestedDestination` covers repository recreation at `NotificationRepositoryTest.kt:402-417`. Keep this repair separate from the move and retain the test.
2. `NotificationActivity.Unknown.validatedDestination` can also contain an in-app destination, but `encodeActivity` persists only a server destination. The top-level notification destination normally preserves navigation, but the nested activity field itself is not round-trip complete for that domain value. No current mapper creates this combination. Decide whether the nested field should be server-only or whether both destination variants need a separate repair. Do not change it during extraction.
3. `Post.contentVisibility` is used by the notification UI (`NotificationsScreen.kt:154` and `NotificationRow.kt:169`) and is populated by protocol mappers, but `encodePost` and `decodePost` omit it. A persisted filtered or hidden notification post can therefore decode as visible after restart. This is a user-visible content-safety risk. Add a separate approved format change and migration plan if the field must survive persistence; do not add it as an unreviewed codec move.
4. `NotificationGroup.actorContinuation` exists in the domain model but is not written or read. It is not currently populated by protocol mappers or consumed by notification UI, so the current omission has no active continuation path. Preserve the omission for this move and decide separately whether grouped actor pagination will become durable.
5. Corrupt Room JSON can prevent observation while corrupt legacy-file JSON is treated as absent. The current reports already identify this as a storage concern. Codec extraction must not hide the difference by adding broad catches or by discarding valid state sections.
6. Current tests cover repository behavior and a few persistence cases, but they do not provide fixed historical JSON fixtures for the full version-2 contract. Round-trip tests alone could pass after an encoder and decoder change together.

## Refactor order

1. Add fixed version-2 compatibility fixtures and pure codec characterization tests before moving code. Include one old stored object with omitted modern fields, legacy reaction `imageUrl`, target-only navigation, connected push registration with only the old endpoint, unknown enum values, and malformed array entries.
2. Add complete state fixtures for all unread states, settings including an empty category set, checkpoints with opaque cursors, dismissal IDs, delivery claims and leases, push registration failures, grouped notifications, recursive quotes, nullable interaction counts, and custom emoji.
3. Move the recursive helper block from `NotificationRepository.kt:525-1094` into `NotificationJsonCodec.kt`. Keep the existing top-level `encode` and `decode` names and signatures so `NotificationStore.kt` does not need a behavioral API change.
4. Make recursive helpers private to `NotificationJsonCodec.kt`. Keep only the state entry points package-visible. Preserve imports and avoid duplicate helper implementations.
5. Keep `NotificationStore.kt` as the only caller of state-level JSON conversion. Verify that `FileNotificationStore`, `RoomNotificationStore`, and `LegacyNotificationFileImporter` still use the same codec path.
6. Move `AccountId.stableFileName` to storage support and `stableNotificationId` to page/delivery support only in separate, behavior-neutral cleanup slices. Do not put either helper in the codec.
7. Run focused codec, repository, settings, push, Room, and legacy-import tests. Review the diff for unchanged JSON keys, omission rules, enum strings, defaults, and exception boundaries.
8. Run the broader notification sync, launch routing, presentation, adapter contract, and account-isolation suites. Keep the `contentVisibility`, nested in-app unknown destination, group continuation, and corruption decisions outside this extraction unless separately approved.

## Regression tests

The focused coverage should include:

- `NotificationJsonCodecTest` with fixed JSON fixtures. Assert field-level output and decoded values without depending on object key order.
- Encode/decode round trips for every notification activity, every target and destination, all unread states, read-state flags, grouped and ungrouped notifications, optional fields, recursive quotes, attachments, reactions, emoji choices, nullable counts, settings, delivery records, checkpoints, and push registrations.
- Fixed old JSON fixtures for v0.2.1 atomic-file data and for the Room `stateJson` blob. Assert that old omissions and legacy fallbacks remain readable.
- Unknown and unsupported values: unknown activity and system kinds, unknown enum values, malformed URLs, invalid protocol values, unsupported media kinds, malformed counts, invalid cursor sections, and malformed list entries.
- Malformed top-level data for `FileNotificationStore` and `RoomNotificationStore`. Characterize the current absent-state behavior for the file store and thrown-read behavior for Room before any separate corruption policy is selected.
- Repository state serialization through `NotificationRepositoryTest`, including local seen, server acknowledgement, Android presentation, Android dismissal, dismissal tombstones, claim IDs, claim expiry, retry state, settings, push registration, and account-scoped state.
- `RoomNotificationStoreInstrumentedTest` for JSON state round trips, deletion, and legacy import. Add marker-present, marker-absent, absent-file, and malformed-file cases.
- `NotificationSettingsTest` and `PushRegistrationRepositoryTest` for persisted settings, empty category selection, complete push fields, restart token recovery, endpoint fallback, and session revision checks.
- `NotificationAdapterContractTest`, `MastodonNotificationSyncTest`, and `MisskeyNotificationServiceTest` after the move to ensure protocol mappers still produce the same domain values and sync paths still persist them.
- `NotificationRouteResolverTest`, `NotificationLaunchRouterTest`, `NotificationsViewModelTest`, and notification presentation tests for destinations, account ownership, and persisted notification rendering.
- Account-isolation tests for two accounts with similar local IDs, foreign entity origins, restart loading, account removal, and late writes. The codec should remain a pure converter; repository and store tests own the isolation assertions.

## Release-blocking verification

The move is release-blocking until all of these checks pass:

- No JSON helper listed above remains in `NotificationRepository.kt`, and no duplicate implementation exists in the codec or another store.
- `NotificationStore.kt` still writes version `2` and reads the same state shape for both atomic files and Room blobs.
- Fixed historical fixtures decode with the same values, defaults, skipped entries, URL validation, and legacy fallbacks as the current implementation.
- The current unknown server-destination repair remains green.
- Repository state, delivery claims, push registration, settings, and account removal retain their current synchronized ownership.
- Focused notification tests pass, followed by `gradlew.bat test assembleRelease` and `gradlew.bat lintDebug`.
- `gradlew.bat connectedDebugAndroidTest` passes the Room persistence and legacy-import coverage on an available device. Instrumented success does not prove live server behavior or all physical-device notification delivery behavior.
- No application source or test changes were made during this review. No build, device, or live-server verification was run for this report.

The `Post.contentVisibility` loss and the malformed Room state policy require separate decisions before they can be called resolved. They should remain visible in release review even if the codec extraction itself is behavior-preserving.

## Open questions

- Is `Post.contentVisibility` intentionally transient for notification persistence, or must filtered and hidden notification posts retain their visibility state after restart?
- Should `NotificationGroup.actorContinuation` become part of the durable contract, or should the unused domain and schema fields be removed in a separate grouped-notification design?
- Should `NotificationActivity.Unknown.validatedDestination` support in-app targets, or should its type be narrowed to validated server destinations?
- What is the approved recovery policy for malformed Room JSON: fail observation, delete the account blob, preserve valid sections, or require an explicit repair flow?
- Should the stored `version` remain ignored for compatibility, or should a future migration introduce explicit version dispatch? The extraction must keep the current ignored behavior.
- Should `AccountId.stableFileName` and `stableNotificationId` be moved as separate cleanup slices, or should their current file placement remain until a later storage and delivery decomposition?

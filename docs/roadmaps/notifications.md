# Complete notifications for Misskey and Mastodon

Prepared September 7, 2026 against app commit `3834e3ef74111b1423fc3c7d451819716590dbe8`. This is an implementation plan, not completed notification functionality. The existing application was inspected directly. Protocol references were checked against official documentation and Misskey source; moving documentation and Misskey `develop` references must be pinned to tested releases in milestone 0.

**Build one complete, account-scoped notification system with two protocol adapters and UnifiedPush delivery.** It must provide a usable inbox, accurate read indicators, working destinations and actions, durable multi-account state, live foreground updates, Android alerts, preferences, and recovery after disconnection or process death. UnifiedPush is a requirement: do not add Firebase Messaging, an embedded FCM distributor, or an implicit FCM fallback. An unavailable distributor leads to a visible setup/recovery state and optional periodic checks.

The core design is that notifications belong to the receiving account. The inbox, badge, stream, periodic reconciliation, and push handler all use the same repository. No screen or push callback may maintain its own competing unread counter or switch credentials based on whichever account happens to be visible.

1. **Define the finished experience and the current gaps.**

   Keep the existing Notifications destination, compact navigation, and Material 3 visual language. The UI represents all notifications with no selected filter; `Replies`, `Reposts`, and `Likes` are toggleable chips in that order, and tapping the selected chip clears the filter back to all notifications. Later work must attach typed protocol-neutral queries, persistence, read state, account switching, and mapping for each category without restoring an `All`/`Mentions` tab bar. Account-switcher badges identify activity on other accounts; a combined all-account inbox is a future product option, not necessary for reliable multi-account delivery.

   A notification row shows the actor or appropriate system identity, activity description, time, unread/seen indication where supported, and a safe post or event preview. Tapping the actor opens the profile. Tapping post activity opens the correct note or status and conversation under the receiving account. Follow requests expose accept/reject. Other ordinary post actions reuse shared action handling and are shown only when actually supported. Deleted/private targets remain understandable rows with an unavailable-target state.

   Provide initial loading, refresh, pagination, cached offline data, empty-filter, empty-inbox, permission-upgrade, authentication-expired, and retry states. A failed refresh must not replace cached notifications with an empty screen. New arrivals should preserve the current scroll position and offer a new-activity indicator when the user is reading older items.

   The current implementation has these concrete gaps:

   | Existing area | Finding | Planned change |
   |---|---|---|
   | `domain/Notification.kt` | String type, mandatory actor, optional post, default `isRead=false` | Typed kinds and targets, optional/multiple actors, explicit read knowledge and ownership |
   | `SocialModels.kt` | Only `notifications(cursor)`; event stream defaults to unsupported | Query, reconciliation, acknowledgement, capabilities, subscription operations and typed events |
   | `MisskeySource.kt` | No notifications override | Full Misskey notification adapter and mapping |
   | `MastodonSource.kt` / `MastodonMapper.kt` | Basic v1 listing; every mapped item inherits `isRead=false` | Filters, robust payload mapping, markers, grouping, policy and push operations |
   | `AccountSyncCoordinator.kt` | Polls the first page every 60 seconds and counts `!isRead` | Repository-driven sync with authoritative or explicitly limited unread knowledge |
   | `FeedViewModel.kt` | Owns registration/unregistration of notification polling | Move account sync lifetime out of feed-screen lifetime |
   | `Screens.kt` / `PalustrisApp.kt` | Placeholder notification panel | Account-scoped state and complete inbox navigation |
   | Auth and manifest | Misskey lacks notification permissions; Mastodon requests `read write`; no Android notification permission or push integration | Compatible permission upgrades, UnifiedPush lifecycle, Android presentation |

   Mastodon's mapper does not establish which items are read; therefore counting that page cannot produce a correct unread total. The current poller also catches cancellation as a general exception and checks generation before, rather than after, a suspended fetch. Address both when replacing it, with regression tests proving late responses cannot revive removed-account state.

   Direct-message conversations remain a distinct feature. Mention notifications for private posts must work, but this roadmap does not turn the existing Messages placeholder into a chat client. Chat/antenna push event families must be recognized and routed to an explicitly supported destination or safely ignored; they must not be mislabeled as ordinary notifications.

2. **Milestone 0 — freeze protocol contracts and prove UnifiedPush feasibility.**

   Before substantial UI work, create a compatibility document and synthetic fixtures for a pinned stable Misskey release, the deployed Misskey-family variants intended for support, a current stable Mastodon, and an older Mastodon without grouped notifications. Record versions, permissions, supported kinds, pagination, read semantics, filtering, stream events, push encoding, and missing-feature behavior. Newer types visible in moving documentation are capability-gated candidates, not a promise that every deployed server supports them.

   Verify these protocol differences explicitly:

   | Concern | Misskey | Mastodon |
   |---|---|---|
   | Basic listing | `POST /api/i/notifications`, `sinceId`/`untilId`, include/exclude types | `GET /api/v1/notifications`, type filters and Link pagination |
   | Read behavior | Send `markAsRead=false` on every fetch; current source otherwise marks all read | Listing is separate from notification timeline markers |
   | Server acknowledgement | `POST /api/notifications/mark-all-as-read` is account-wide | Read/write `/api/v1/markers` for the notifications timeline |
   | Unread knowledge | Inspect authenticated user fields; count or boolean depends on version | Prefer supported unread-count endpoint; otherwise reconcile markers and retained history |
   | Grouping | Optional `i/notifications-grouped`, with its own paging semantics | Optional `/api/v2/notifications`, opaque group identity and actor expansion |
   | Push subscription | `sw/register`, update/unregister lifecycle | `/api/v1/push/subscription`, separately granted `push` scope |

   Misskey's current listing explicitly defaults `markAsRead` to true and invokes an account-wide read operation. This is a correctness requirement for every request path, including retries, filtered queries, and grouped listing. [Misskey listing source](https://raw.githubusercontent.com/misskey-dev/misskey/develop/packages/backend/src/server/api/endpoints/i/notifications.ts), [read-all source](https://raw.githubusercontent.com/misskey-dev/misskey/develop/packages/backend/src/server/api/endpoints/notifications/mark-all-as-read.ts).

   Run an early end-to-end UnifiedPush spike against both test servers: choose a distributor, obtain an account-specific endpoint and encryption key material, register with the social server, generate a controlled event, receive and decrypt it, then unregister. Test a device without Google Play Services. This settles the transport and Web Push encoding before the rest of the feature depends on it. Select and pin the maintained UnifiedPush connector release at implementation time, including its actual service API and dependency graph. [UnifiedPush connector documentation](https://unifiedpush.org/kdoc/connector/).

   Prefer direct delivery from the social server to the distributor's Web Push endpoint. Mastodon exposes a standards-mode subscription option on newer servers; older servers may send legacy Web Push encoding. Test that explicitly against the chosen connector instead of assuming compatibility. If an older target needs a compatibility gateway, document its encoding, privacy, deployment and maintenance requirements and settle support for that target before calling push complete. A gateway, if needed, must still deliver through UnifiedPush and must not receive account access tokens. [Mastodon push subscription contract](https://docs.joinmastodon.org/methods/push/).

   **Exit criteria:** a pinned support matrix, fixtures for both protocols, a recorded successful push round trip for each baseline, and explicit handling for unsupported versions. Development can use synthetic fixtures; claims about authenticated delivery require actual test accounts and devices.

3. **Milestone 1 — establish domain contracts and permission upgrades.**

   Replace the string-plus-boolean model with a typed notification envelope. Preserve an opaque server notification ID, receiving `AccountId`, creation time, optional actor previews, typed activity, typed destination, optional canonical post snapshot, and normalized read information. Keep the raw type identifier for diagnostics and forward compatibility, but never expose raw server payloads through UI state or logs.

   Define ordinary activity variants for mention, reply, reshare, quote, favourite, emoji reaction, follow, follow request, accepted request, subscribed-user post, poll result, and post update. Define structured system/event variants for moderation, relationship changes, role/achievement, app events, and other supported notifications. Include `Unknown` with safe fallback text and an optional validated destination. A missing actor or post must not make a whole page fail. Reaction information must preserve Unicode/custom emoji identity, image URL where supplied, and textual fallback.

   Separate notification identity from group identity and target identity. Group rows retain actor samples, total count when known, and a continuation for actor expansion. Their keys are account-scoped. They are presentation aggregates, not replacement notification IDs; changing group membership must not generate a brand-new OS alert for every existing member. Likewise, a renote/reblog wrapper must not become the target ID for a reaction or reply to the original post.

   Extend `SocialSource` with cohesive notification operations, using proposed types such as `NotificationQuery`, `NotificationPage`, `NotificationCheckpoint`, `NotificationReadState`, and `PushSubscriptionSpec`. Include fetch-newer/reconciliation, fetch-older, unread-state retrieval, acknowledgement, supported dismissal, follow-request actions, and subscription create/update/remove. Give unsupported operations normalized `SourceError.Unsupported` results. Keep tokens, HTTP URLs and protocol parameter names inside adapters. A push parser may produce an account-bound domain event through the source boundary; Android services must not reach directly into concrete adapters.

   Add a notification capability object that distinguishes listing, supported categories, read semantics, unread-count precision, server grouping, dismissal, policy management, follow-request actions, streaming, and Web Push support. Effective availability combines server support, granted access and implemented behavior. A forbidden request is not proof that the server lacks the feature. Only verified endpoint/version evidence should disable a capability; connectivity failures must remain retryable errors. Preserve account capability values through serialization, cache refresh and reauthentication.

   Upgrade Misskey MiAuth with `read:notifications` and `write:notifications`; add the verified relationship permissions only for actions included in this feature. Preserve its existing permissions. Add Mastodon's `push` scope to application registration and authorization when enabling push. Existing `read write` covers broad access but does not replace `push`. Track requested versus known-granted access honestly, including unknown state for migrated sessions. Update the origin-scoped registration cache to account for scope compatibility without making app registrations account-scoped.

   Permission upgrades replace only the intended account's session after successful authentication. Cancelled or failed upgrades preserve its old usable session and all other accounts. Verify returned identity before replacement; signing in as a different account must not overwrite the account being upgraded. Do not infer new permissions for an old token merely because the app's requested scope changed.

   **Exit criteria:** shared contract tests compile against both sources; unknown/system notifications survive mapping; old sessions restore; permission upgrades are account-safe; capabilities accurately distinguish denied, unsupported and temporarily unavailable.

4. **Milestone 2 — complete both REST adapters and their notification types.**

   Implement Misskey listing first, including filters, older/newer traversal and explicit non-mutating fetch behavior. Add a dedicated notification mapper instead of making the post mapper responsible for activity semantics. Current Misskey source also includes actorless and system events, and grouped reaction/renote shapes; handle their supplied fields rather than requiring every payload to contain `user` and `note`. Preserve usable legacy/fork types through tested mappings and unknown fallback. [Misskey notification model](https://raw.githubusercontent.com/misskey-dev/misskey/develop/packages/backend/src/models/Notification.ts).

   Expand Mastodon v1 mapping and query support as the common compatibility path. Cover mentions, favourites, boosts, follows and requests, subscribed posts, polls, updates, quotes, moderation warnings, reports and severed relationships. Add newer collection/fallback variants only where the pinned matrix supports them. Preserve type-specific targets: for example, the status attached to `quoted_update` is the user's quote, which needs different wording/navigation from the edited source. [Mastodon notification entity](https://docs.joinmastodon.org/entities/Notification/).

   Keep returned cursors opaque above the adapter. Bind them to account, query and API variant so a Mentions continuation cannot be reused for All or for another account. Validate scheme, host and port before authenticated pagination, and audit redirect handling so a validated first URL cannot redirect credentials to another origin. Restrict relative continuations to valid notification routes. Encode supplied IDs as path segments or parameters, never by unsafe string concatenation.

   Use separate historical and catch-up continuations. A busy account can receive more than one page while offline: repeatedly fetching only the latest page loses the middle. Traverse the newer range to the previous checkpoint with a bounded work budget, persist continuation when more remains, and advertise a gap rather than silently declaring sync complete. Advance cursors from transport order, not timestamp parsing or Kotlin numeric/lexical ID comparisons. Empty filtered/packed pages and repeated cursors require explicit termination tests; page length alone is not a universal end-of-history signal.

   Add grouping after ungrouped correctness. Mastodon's grouped response has separately referenced actors/statuses and server group keys; support actor expansion and query-consistent unread counts. Misskey's grouped endpoint aggregates fetched activity differently, so do not reuse Mastodon group/cursor assumptions. Maintain an ungrouped reconciliation path where grouped payloads cannot prove event membership or read progress. [Mastodon grouped notifications](https://docs.joinmastodon.org/methods/grouped_notifications/), [Misskey grouped source](https://raw.githubusercontent.com/misskey-dev/misskey/develop/packages/backend/src/server/api/endpoints/i/notifications-grouped.ts).

   **Exit criteria:** fixtures and request assertions cover every supported kind, null/deleted targets, filters, both pagination directions, grouping, malicious continuations, rate limiting, revoked access, unknown types and malformed individual records. A bad optional field cannot erase a valid page; corrupt required identity produces a diagnosed mapping failure rather than fabricated IDs.

5. **Milestone 3 — durable repository, read state and account lifecycle.**

   Introduce `NotificationRepository` plus an account-scoped persistent store. Use it as the single writer for REST pages, stream events, push hints, local actions and acknowledgement outcomes. A transactional Room store is the proposed choice because concurrent ingestion, pagination checkpoints, pending operations and delivery deduplication need atomic updates and indexed queries. Record the dependency reason when implemented. Persist a bounded history, read checkpoints, query continuations, delivery records, preferences and pending synchronization state. Define a concrete retention cap and migration policy in the implementation; deleting cached history must not reset read or delivery checkpoints.

   Notification content may contain private posts. Store it only in app-private storage; keep session secrets and push key material encrypted and out of the notification database unless independently encrypted. Exclude sensitive cache, connector identity and push state from inappropriate backup/device transfer. Use the established encrypted account storage for app-owned secrets, audit the connector's own key storage, and support key deletion on logout. Test schema upgrades and recovery from a corrupt cache without losing valid sessions.

   Represent unread knowledge as exact count, capped/lower-bound count, unread-present boolean, known none, or unknown, with freshness. Render an exact count only when supported; use a dot for boolean/unknown-positive state. Current Misskey user packing includes both a legacy unread flag and a newer count, while individual packed notifications need not have `isRead`. Negotiate these fields instead of manufacturing a false boolean default. [Misskey authenticated-user packing](https://raw.githubusercontent.com/misskey-dev/misskey/develop/packages/backend/src/core/entities/UserEntityService.ts).

   Keep four states separate: fetched, locally seen, acknowledged to the server, and already presented as an Android alert. Android dismissal is another local presentation event. None should accidentally imply the others. First synchronization establishes an alert baseline and caches existing history without ringing for the backlog. Events arriving after that boundary still qualify; include a bootstrap-race test. Never present the first page length as the total unread count.

   Use explicit “Mark all read” as the initial shared server acknowledgement action. Opening the tab, refreshing, receiving push, scrolling a filtered view or swiping away an OS notification does not mark the entire server inbox read. Locally seen styling can update on visibility, but must be labeled/handled as local knowledge when no per-item server read state exists.

   For Mastodon, capture a notification timeline boundary, serialize marker writes, handle marker conflicts by rereading and reconciling, and avoid overwriting a newer known boundary from another device. Do not compare opaque IDs in shared code. Acknowledgement can cross categories, so never advance the account-wide marker implicitly from Mentions. For Misskey, the explicit read-all call acknowledges whatever the server considers current at execution; it cannot promise snapshot-bounded semantics. Reconcile afterward and document/test a notification arriving during that call. [Mastodon marker API](https://docs.joinmastodon.org/methods/markers/), [Misskey read-state implementation](https://raw.githubusercontent.com/misskey-dev/misskey/develop/packages/backend/src/core/NotificationService.ts).

   Persist bounded Mastodon acknowledgements for retry. Do not automatically replay an old offline Misskey “mark all read” later if doing so would acknowledge newly arrived unseen items; retain local seen state and require a fresh intentional server-wide action. Keep dismiss/clear operations distinct from read actions, with clear UI wording and confirmation for destructive server history removal.

   AccountManager remains the session authority; AccountSyncCoordinator supervises account work; FeedViewModel remains responsible for the feed. Introduce a session/source provider usable by background workers and let the coordinator observe available accounts independently of feed creation. An application-lifetime sync owner may consume the same account store without creating a UI ViewModel in a worker.

   Fence every write by account/session generation after suspended operations. Logout cancels work, removes cache/preferences/pending actions and displayed alerts for that account, unregisters its push connection, and prevents late callbacks from recreating state. Reauthentication replaces sources/subscriptions without replaying previously delivered alerts. A failure in one account cannot cancel another account's work.

   **Exit criteria:** restart/offline recovery, overlapping ingestion, more-than-one-page catch-up, read races, same-origin multiple accounts, cancelled upgrade, account removal during a request, and late callbacks all preserve correct ownership and state.

6. **Milestone 4 — finish the inbox and action journeys.**

   Add `NotificationsViewModel`, `NotificationsState`, a dedicated screen and reusable row components. Inject the repository and receiving account; do not put notification lists into FeedViewModel. Connect the screen in `PalustrisApp`, preserving existing navigation and the separate Direct messages toggle.

   Implement the null/all view and typed Replies, Reposts, and Likes queries behind the existing chip state, then add pull-to-refresh, paged history, stable list keys, new-arrival positioning, grouped actor expansion, account badges, cached content and useful retries. Keep unread totals distinct from filtered result counts. Restore scroll/filter state per account and query across navigation and process recreation.

   Reuse existing post text, content-warning and sensitive-media presentation, with compact previews. Allow actorless/system rows and custom-emoji reactions. Accessibility includes descriptive activity text, localized/pluralized actor counts, readable dates, large fonts, TalkBack, adequate touch targets, and read-state cues beyond color. Verify light/dark themes and phone/wide layouts against rendered screens.

   Complete account-bound post/profile routing as part of this milestone. Supply missing native detail behavior needed by ordinary notifications and adapter-backed accept/reject for follow requests. Route a cold-start Android tap through account restoration before fetching its target. If the account was removed, show an explanatory destination rather than using the currently selected account. For advanced administrative or server-specific objects outside existing native features, show meaningful event details plus a verified HTTPS “Open on server” destination. A generic dead row does not count as support; broader moderation/chat/collection editors remain separate features.

   Preserve server filtering. Add Mastodon notification-request review and policy controls where supported, including accept/dismiss and delayed merge reconciliation; these requests are distinct from follow requests. Misskey notification-receive preferences should use the tested server configuration API when available. Display device alert preferences separately from server-wide delivery/filtering preferences, and preserve unknown server settings when updating known fields. [Mastodon notification methods and policies](https://docs.joinmastodon.org/methods/notifications/).

   **Exit criteria:** ordinary notification journeys work from list to target/action on both protocols; rare types remain informative and actionable through an explicit supported destination; offline, empty, error and denied-access states are rendered and tested.

7. **Milestone 5 — UnifiedPush subscriptions and Android alerts.**

   Add the maintained UnifiedPush connector and an app push manager. Use a stable random registration instance per receiving account and installation, mapped privately to `AccountId`; never use an access token as the distributor identifier. Honor the user's current/default distributor and provide selection/change controls. Show account-level states such as Off, Choose a UnifiedPush service, Registering, Connected, Permission needed and Temporarily unavailable. “Connected” means both distributor registration and social-server subscription succeeded, not merely that an endpoint callback arrived. [UnifiedPush registration instances](https://unifiedpush.org/kdoc/connector/org.unifiedpush.android.connector/-unified-push/register.html), [UnifiedPush setup UX](https://unifiedpush.org/developers/ux/).

   Store desired subscription separately from confirmed remote subscription. Persist account generation, endpoint generation, distributor selection, server subscription metadata and retry state. Handle new endpoints, duplicate callbacks, temporary endpoints, distributor removal, registration failure, app updates and restored installations. Endpoint rotation must replace the corresponding server subscription and retire obsolete registrations safely. Check generation before every mutation so an old endpoint callback cannot overwrite a new login.

   For Mastodon, submit the UnifiedPush endpoint and Web Push public/auth keys, supported alert selections and verified encoding option. The token's subscription is a single slot; re-registration must update that account's slot deliberately. For Misskey, submit the endpoint, `auth`, `publickey` and tested read-message preference through `sw/register`; use update/unregister for their documented purposes, and remove superseded endpoints after a successful replacement. Fetch the social server's VAPID public key through verified metadata where required by the distributor. Do not confuse that server identity key with the device's encryption keys. [Misskey subscription registration](https://raw.githubusercontent.com/misskey-dev/misskey/develop/packages/backend/src/server/api/endpoints/sw/register.ts), [subscription updates](https://raw.githubusercontent.com/misskey-dev/misskey/develop/packages/backend/src/server/api/endpoints/sw/update-registration.ts).

   Use the pinned connector's supported push service and decryption facilities. Its current `PushService` receives decrypted content and endpoint lifecycle events; follow that release's manifest contract instead of copying outdated receiver snippets. Keep callback work bounded: validate account/registration generation, persist a minimal event or refresh hint, and enqueue account-unique reconciliation when network work is necessary. [UnifiedPush PushService](https://unifiedpush.org/kdoc/connector/org.unifiedpush.android.connector/-push-service/).

   Parse protocol payloads into distinct notification, read-state and unrelated event variants. Misskey push payloads may contain shortened note summaries and omit normal post fields, so they cannot simply be sent through the full REST post mapper. Incomplete payloads trigger authenticated reconciliation. Suppress body previews until content-warning/privacy information is known; a generic account-level alert is acceptable when content cannot safely be established. Account credentials come only from local encrypted sessions, never from URLs or token-like fields in push payloads. [Misskey push payload construction](https://raw.githubusercontent.com/misskey-dev/misskey/develop/packages/backend/src/core/PushNotificationService.ts).

   Deduplicate persistently by receiving account and canonical notification identity. If a push is only a refresh hint, reconcile before assigning an event identity. Use stable Android notification tags and a persisted delivery outbox so a crash around posting can update the same alert without repeatedly sounding it. REST, stream and push delivery of one event must converge on one row and at most one audible alert. Update grouped OS summaries silently as membership changes. Remote read events trigger account-bound reconciliation and cancellation only where read coverage is known.

   Add `POST_NOTIFICATIONS` and request it in context when the user enables device alerts. Denial leaves the inbox working and settings explain how to enable alerts. Use stable channels for parallel categories such as mentions/replies, social activity and account/system events, grouped by account where appropriate. Respect Android channel settings, lock-screen preview controls, DND and sound choices. Default private/sensitive content to concealed previews; optionally show only a generic account notification. [Android notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission).

   Use explicit, account-bound pending intents with immutable flags except where a verified feature requires otherwise. Opening a notification is the first release action; inline replies are a later enhancement because they require reliable account-bound reply composition, recipient semantics and retry behavior. Dismissing an Android alert does not delete server history or imply read-all. Suppress redundant sound while the same activity is visibly being read, while preserving other accounts' delivery preferences.

   Logout first fences delivery locally, then attempts remote subscription cleanup with the existing session, unregisters that account's UnifiedPush instance and clears keys and displayed alerts. An offline remote cleanup failure must not block logout or retain the access token indefinitely. Report that cleanup outcome in non-secret diagnostics and reject subsequent callbacks using the removed registration. Test distributor changes with multiple accounts and verify that one account's removal leaves the others subscribed.

   **Exit criteria:** real Misskey and Mastodon events reach a release build through UnifiedPush on a device without Play Services; denied permission, missing/removed distributor, endpoint changes, malformed messages, process death, duplicate delivery, cold-start navigation and logout all behave correctly. Verify the packaged dependency graph contains no FCM integration.

8. **Milestone 6 — foreground streaming, recovery and delivery settings.**

   Implement account-bound typed stream events through `SocialSource`. Use Misskey's authenticated main channel and Mastodon's supported user-notification stream, normalizing notifications, read changes and relevant invalidations. Respect declared streaming origins and establish trusted server-provided endpoint rules before authentication; do not reuse arbitrary URLs from events. Reconnect with exponential backoff and jitter, propagate cancellation, and reconcile REST gaps after reconnect. Streams improve freshness; they do not replace durable retrieval. [Misskey main channel](https://raw.githubusercontent.com/misskey-dev/misskey/develop/packages/backend/src/server/api/stream/channels/main.ts), [Mastodon streaming](https://docs.joinmastodon.org/methods/streaming/).

   Avoid keeping a permanent app-owned socket alive in the background to simulate push. Use foreground streaming while useful and UnifiedPush when backgrounded. Coalesce simultaneous push, app-resume and stream reconnect requests into one account sync job. Handle rate limits with server retry guidance, distinguish network failure from revoked credentials, and stop automatic retry loops for unrecoverable authorization failures until the account is repaired.

   Add WorkManager for durable subscription retries, push-triggered reconciliation and optional periodic fallback. Keep jobs account-unique and constraints explicit; re-read the session and generation when a worker starts. Periodic work is delayed by Android and has a minimum 15-minute interval, so present it as periodic checking rather than instant delivery. Propose 30-minute default checks when the user opts into fallback, adjustable within supported scheduling limits. No distributor should produce a clear setup option and continued foreground refresh, not an invisible transport substitution. [Android periodic work behavior](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work).

   Settings cover per-account alert enablement, categories, preview privacy, quiet hours, distributor selection/status, periodic fallback and server-supported policies. Persist local preferences across reauthentication. Distinguish selected preferences from successfully applied server settings; failed changes remain visible and retryable. Quiet hours suppress immediate sound without deleting inbox activity. Include a local presentation test and a separate real delivery diagnostic so users are not told that a locally generated notification proves server push is healthy.

   **Exit criteria:** reconnect catches up without gaps or duplicate sounds; inactive accounts receive push; quiet hours and OS settings work together; retries survive process death; the app describes degraded delivery accurately.

9. **Milestone 7 — release verification and completion gates.**

   Build a reusable notification source contract suite exercised by both adapters, then focused mapper, repository, coordinator, permission-upgrade and push-lifecycle tests. Use synthetic protocol fixtures and controlled test accounts; never record tokens, MiAuth IDs, auth headers, full private response bodies, distributor endpoint secrets or encryption keys in logs.

   | Verification layer | Required evidence |
   |---|---|
   | Adapter contracts | Request methods/permissions, non-mutating fetches, kind mapping, cursors, marker semantics, grouping, policy and subscription lifecycle |
   | Persistence and concurrency | Atomic ingestion/checkpoints, migration, duplicate sources, late callbacks, initial-sync race, read/new-arrival races, account removal and crash recovery |
   | Compose/navigation | Null/all plus Replies/Reposts/Likes filter states, badge precision, account switch, grouped rows, target actions, TalkBack/large fonts, light/dark and wide layouts |
   | Android presentation | Channels, denied permission, lock-screen privacy, quiet hours, stable IDs, grouping, cold-start pending intents and removed-account taps |
   | Real protocol delivery | Misskey plus Mastodon, multiple accounts on the same server, multiple origins, two maintained UnifiedPush distributors, endpoint replacement and server read reconciliation |
   | Device resilience | Device without Play Services, process death, reboot/unlock, Doze, offline recovery, distributor removal and token revocation |

   Explicitly distinguish ordinary process death from Android force-stop; record the platform's recovery behavior and do not promise delivery while the application is force-stopped. Test a second client marking notifications read and a reconnect after more than one page of activity. Verify release packaging as well as debug behavior.

   For each implementation slice, run relevant focused tests with `./gradlew :app:testDebugUnitTest --tests <fully-qualified-test-class>`. Auth, session, storage, adapter and contract changes also require `./gradlew lintDebug`. Before completing each scoped task, run `./gradlew test assembleRelease`, update the task logs, and make a focused commit after successful validation when permitted. Every proposed dependency must have its reason recorded in `logs/DONE.txt`.

   Completion requires: both supported server baselines render and route ordinary notifications; all supported event families have a meaningful presentation; filtering and read state are honest; account state survives restart; actions use the receiving account; UnifiedPush delivers verified Android alerts; duplicates and late callbacks are safe; permission upgrades and logout preserve other accounts; and runtime evidence is recorded. A passing mocked suite or a working placeholder screen does not meet that definition.

10. **Implementation order, file ownership and decisions.**

    Execute milestones 0–7 in order. Milestone 0 proves the main transport risk early; milestone 1 fixes the contract; milestones 2–3 establish correct data; milestone 4 finishes in-app workflows; milestone 5 completes background push and alerts; milestone 6 hardens freshness and preferences; milestone 7 is the release gate. Tests accompany each milestone rather than being postponed to the end. Deliver small commits within milestones, and avoid combining both adapters, UI, persistence and Android services into one unreviewable patch.

    | Area | Existing files to change | Proposed additions |
    |---|---|---|
    | Domain | `domain/Notification.kt`, `SocialModels.kt`, `Event.kt`, `ServerCapabilities.kt`, session capability serialization | Notification queries, read state, destinations and subscription models |
    | Protocol | `data/misskey/MisskeySource.kt`, `data/mastodon/MastodonSource.kt`, `MastodonMapper.kt`, capability/error mapping | Dedicated notification/push mappers and protocol contract fixtures |
    | Account/auth | `MisskeyAuth.kt`, `MastodonAuth.kt`, `AppRegistrationCache.kt`, `SessionStore.kt`, `ui/AccountManager.kt` | Permission-upgrade metadata and background session provider |
    | Persistence/sync | `ui/AccountSyncCoordinator.kt`, `FeedViewModel.kt`, dependency wiring | `data/notifications/` repository/store, migrations and workers |
